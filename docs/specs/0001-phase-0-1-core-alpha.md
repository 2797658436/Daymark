# Daymark 阶段 0＋1：桌面骨架与手动行动闭环

## Problem Statement

拖延用户往往已经积累了许多没有明确结束时间的任务，但真正可用的时间有限。普通待办工具只负责收集，传统日历又要求用户先完成大量拆解和排程；当任务错过或只推进一部分时，系统还容易制造越来越多的欠账，使用户最终放弃维护计划。

Daymark 需要先验证一个最小但完整的行动闭环：用户能快速记录任务，把它安排到真实时间，看到当前应该处理什么，主动记录一次开始与结束，手动确认推进程度，并在应用重启后继续从同一事实状态工作。该闭环必须本地可靠、容易撤销、没有羞辱性反馈，且为后续自动排程、重复习惯和回顾保留正确的数据基础。

## Solution

阶段 0 建立 Windows 桌面应用、版本化本地数据、主题框架、备份恢复和核心领域对象。阶段 1 在该骨架上交付一个供 3 天稳定性试用的手动行动闭环：今日页、任务池、普通项目、文本课程导入、日／周日历、基础拖拽排程、默认时段、截止日期、手动完成度、开始／结束本次、精简小结、托盘、自启、启动摘要和执行提醒。

完整 UI 规范继续作为产品目标，但阶段 0＋1 只实现能够验证核心闭环的交互。已经实现的路径必须顺滑、可撤销、可键盘操作并诚实保存；未进入本阶段的高级路径不得以半成品入口出现。

## User Stories

1. 作为容易拖延的用户，我希望只输入标题就能创建任务，从而不因填写表单而放弃记录。
2. 作为用户，我希望稍后补充分类、项目、截止日期和耗时信息，从而先收集再整理。
3. 作为用户，我希望任务即使被安排后仍留在任务池，从而能为长期任务安排多次投入。
4. 作为用户，我希望按全部、尚未安排和已有安排筛选任务，从而快速找到下一步对象。
5. 作为用户，我希望看到逾期和未来七天内截止的任务，从而不遗漏真正紧迫的事项。
6. 作为用户，我希望创建普通项目并在其中维护有序任务，从而把课程或长期成果拆成可执行部分。
7. 作为课程学习者，我希望粘贴分集文本批量建立项目任务，从而不必逐条输入几十个分 P。
8. 作为课程学习者，我希望导入前检查、取消选择和修改分集，从而不会把解析错误写入项目。
9. 作为用户，我希望在日视图中查看完整一天并连续滚动到相邻日期，从而安排跨午夜或凌晨活动。
10. 作为用户，我希望在周视图中观察七天容量，从而发现哪一天仍有可用时间。
11. 作为用户，我希望配置一个或多个默认时段，从而让日历突出我通常愿意投入的时间。
12. 作为用户，我希望折叠非默认时段但仍能看到其中是否有安排，从而保持时间轴简洁而不丢信息。
13. 作为用户，我希望把任务从任务池拖到日历空档，从而用一次直观操作创建执行时段。
14. 作为用户，我希望日历拖拽默认吸附到清晰的时间粒度，从而快速获得整齐时间，同时仍能精确编辑。
15. 作为用户，我希望移动已安排任务时只移动该执行时段，从而不意外复制或改变任务本身。
16. 作为用户，我希望拖动执行时段底边调整长度，从而根据当天情况修改投入时间。
17. 作为用户，我希望把执行时段拖回任务池，从而取消本次安排但保留任务和进度。
18. 作为用户，我希望移动、调整和取消安排后可以立即撤销，从而敢于尝试调整日历。
19. 作为用户，我希望在日历空白处框选时间后新建任务，从而同时完成收集和安排。
20. 作为用户，我希望为任务设置截止日期，从而让任务池和今日页显示真实期限风险。
21. 作为用户，我希望任务进度由我手动调整，从而投入时间不会被误当作实际完成度。
22. 作为用户，我希望一个任务可以在多天分次推进，从而不必一次完成整个课程或项目任务。
23. 作为用户，我希望今日页首先告诉我当前安排、待回顾和下一项，从而不必先阅读统计仪表盘。
24. 作为用户，我希望当前时间线和当前安排清晰可见，从而直观判断计划进行到哪里。
25. 作为用户，我希望开始签到默认关闭但可以主动开启，从而按自己的压力承受程度选择是否记录准时启动。
26. 作为开启开始签到的用户，我希望点击“开始本次”才记录实际开始，从而系统不会假装我正在执行。
27. 作为用户，我希望点击“结束本次”只结束这一次执行，从而不会意外把整个任务标记完成。
28. 作为用户，我希望结束后快速修正实际投入、任务进度并可选写下感受，从而保留有用事实而不被强迫复盘。
29. 作为用户，我希望应用重启后仍保留任务、日历、执行记录、进度与页面状态，从而可以持续使用。
30. 作为用户，我希望应用关闭窗口后驻留托盘，从而继续接收执行提醒并快速重新打开今日页。
31. 作为用户，我希望按设置开机自启并收到启动摘要，从而记得查看临期事项而不会被强制打开主窗口。
32. 作为用户，我希望执行提醒只定位到任务而不自动开始，从而最终行动仍由我确认。
33. 作为用户，我希望每天自动生成本地备份并能手动恢复，从而不因试用阶段错误失去计划历史。
34. 作为用户，我希望保存失败时明确看到“未保存”并保留输入，从而不会相信虚假的成功状态。
35. 作为键盘用户，我希望完成创建、选择、打开、取消和撤销等核心操作，从而不被迫使用鼠标。
36. 作为容易被动画干扰的用户，我希望减少动态效果但保留状态反馈，从而既舒适又不会失去操作结果。
37. 作为试用者，我希望三天后能检查安排、实际开始、部分推进、完成和未执行事实，从而判断核心闭环是否可靠。

## Implementation Decisions

- 桌面容器使用 Tauri 2；界面使用 React、TypeScript、Vite、Tailwind CSS、shadcn/ui、dnd-kit 和 Motion。
- 第一阶段只发布 Windows 桌面应用，不单独发布网页版。Web 技术是桌面应用的界面层，而不是独立产品。
- 核心数据存入 SQLite；少量界面与系统偏好存入 Tauri Store。
- 数据库从第一版使用显式 `schema_version`、稳定对象 ID 和可重复执行的版本化迁移。
- 核心对象至少包括 Task、Project、ExecutionSession、ExecutionRecord 和 ProgressEvent；计划时段、实际执行和进度变化不能合并为一个状态字段。
- 时间字段明确区分计划使用的本地日期／时间与实际记录的时间点；跨日和时区变化不得静默改写原始事实。
- 进度变化、执行开始／结束、未执行事实和撤销所需信息从阶段 1 起保存，即使完整回顾页尚未实现。
- 任务是可逐步完成的对象；一个任务可以拥有多个执行时段。项目本身不占用日历，项目任务才会被安排。
- 课程是普通项目的导入方式。阶段 1只要求稳定的文本分 P 导入；B 站链接读取留给阶段 2 Beta。
- 快速创建只有标题必填。完整字段在右侧渐进式面板中补充，不使用阻断式大型弹窗。
- 阶段 1 的任务池实现活动任务、关注区、基本筛选和下一次安排信息；高级分组、自定义排序和批量编辑延后。
- 阶段 1 的日历实现日视图与基础周视图。月视图、独立截止任务页和完整回顾页不显示半成品入口。
- 基础拖拽范围为：放入空档、移动执行时段、吸附开关、调整时长、移回任务池和撤销。
- 复杂插入连锁让位、跨日整组移动、多选整组拖拽、四项以上重叠展开和并行实际执行延后。
- 默认吸附粒度为 15 分钟，并允许用户关闭吸附或精确编辑时间。
- 默认时段可以有多个；阶段 1 支持显示和折叠，但不进行自动排程。
- 任务完成度由用户手动确认。投入时间、计划时长和媒体时长都不得自动改变进度。
- 开始签到默认关闭；开启后开始和结束形成实际执行记录。没有签到的时段显示为未记录，而非自动判迟到。
- 本次小结在阶段 1 保留实际投入修正、任务进度和可选短评；星级、完整感受标签和高级统计可在阶段 2 扩展。
- 今日总进度在没有明确今日目标时不猜测目标达成率，只显示当天推进任务数和任务进度累计增加值。
- 托盘、自启、启动摘要和执行提醒属于阶段 1。系统权限只有在用户主动开启相应能力时请求。
- 自动保存不得要求用户点击保存；失败时保留编辑状态并提供重试或本地恢复副本。
- 每日备份默认保留最近七份；恢复前先创建恢复前备份并验证目标备份。
- 阶段 1只需要暖杏主题，但同时支持浅色、深色和跟随系统。其他颜色主题延后。
- 核心状态不能只靠颜色表达；键盘焦点、减少动态和 Windows 100%–200% 缩放从骨架阶段建立。
- 原型使用内存数据，不连接 SQLite、托盘、通知或真实导入接口；它只验证布局、拖拽语义、状态反馈和操作密度。

## Testing Decisions

- 最高测试接缝是完整用户闭环，而不是单个组件：创建任务 → 安排执行时段 → 开始／结束 → 更新进度 → 重启恢复。
- 领域层测试 Task、Project、ExecutionSession、ExecutionRecord 和 ProgressEvent 之间的外部行为及迁移结果，不断言内部 SQL 或组件实现细节。
- 数据测试使用临时 SQLite 数据库覆盖首次创建、升级迁移、事务回滚、每日备份、恢复前备份和恢复验证。
- 桌面集成测试覆盖关闭到托盘、恢复窗口、开机启动路由、通知点击路由和系统权限拒绝后的真实状态。
- UI 端到端测试覆盖快速创建、任务池拖入空档、移动、调整时长、移回任务池、撤销、进度更新和开始／结束本次。
- 键盘测试覆盖焦点顺序、Enter 打开、Esc 关闭／取消、Ctrl+Z 撤销和核心按钮的可访问名称。
- 视觉行为测试不锁定像素截图作为唯一事实；重点验证缩放、折叠、选中、当前安排、未保存和错误状态仍可识别。
- 性能基线至少使用 200 个任务和 300 个执行时段，验证任务池滚动、日历打开和搜索／筛选不会明显阻塞核心操作。
- 阶段 0 验收：重启后数据与页面状态正确恢复；旧 schema 测试库可升级；保存失败不显示成功；备份可以恢复到干净安装。
- 阶段 1 验收：仅标题任务约 10 秒内可创建；从任务池到日历最多一次拖拽；开始当前安排不超过两个明确操作；所有时间修改可撤销；未开始、部分推进和完成状态在重启后保持一致。
- 3 天 Alpha 验收：连续三天无数据丢失、无无法解释的重复任务、无静默进度变化、无无法撤销的核心排程错误。

## Out of Scope

- 自动排程 Lite、时间块参与排程、基础重复习惯和错过后的挽救流程；这些属于阶段 2 的正式 21 天候选版。
- B 站链接读取、重复课程合并与大规模在线元数据处理；阶段 1只保留文本导入。
- 项目里程碑、级联顺延、截止风险压排和复杂项目节奏。
- 月视图、独立截止任务页、完整日／周／月回顾、PNG／CSV 导出和周期对比。
- 多选整组拖拽、高级批量编辑、复杂插入让位、跨日整组移动和四项以上重叠展开。
- 多套颜色主题、自定义界面、布局版本管理和完整命令中心。
- 云同步、账户系统、团队协作、AI 分类／规划、内嵌 B 站播放器和观看监控。

## Further Notes

- 完整产品方向仍以 `CONTEXT.md` 和 `docs/design/UI-SPEC.md` 为准；本规格只是阶段 0＋1 的交付边界。
- 交互原型是可删除的验证工具，不得直接作为生产实现合并。确定方案后应把结论回写规范，再重新实现正式组件。
- 阶段 1只运行约三天的稳定性 Alpha。自动排程 Lite、基础重复习惯与挽救流程完成后，才开始正式 21 天体验。
- 21 天验证重点是开始阻力、错过后的恢复意愿和持续推进，不以连续打卡、总完成率或惩罚性分数作为成功标准。
