## 1. 需要拍板的

### D1 截止页是否常驻任务池（P4-06 §9.1）

**现状**：`App.tsx:348` 的 `hasTaskPool = page === "today" || page === "calendar" || page === "projects"` —— 截止页**不在**其中。截止页只提供行级「安排」动作（复用预选任务的排程入口，走预览确认），**不能拖拽**。

**要定什么**：截止页要不要像今日页一样常驻右侧任务池。

**怎么测**：把 `hasTaskPool` 加上 `page === "deadlines"`，然后：

```powershell
npm test
npm run test:e2e
```

重点看三处：(a) AC10 用例「跨页返回保留筛选／焦点／滚动」是否仍成立（滚动容器与焦点恢复会被新栏位影响）；(b) 960×640 与 200% 缩放下截止页的筛选是否仍可用（AC14）；(c) 新栏位会不会像今天修的那个问题一样遮挡头部 —— 检查 `#task-pool` 的 `position` 与 `getBoundingClientRect()`。

**真正的难点不在测试**：截止页没有时间轴，「拖到哪」没有语义。要么任务池只是摆设（不能拖，那它的价值基本为零），要么需要重新设计三栏布局与拖拽落点 —— 规格 §6.2 没有定义这件事。

**建议：不加。** 截止页的定位是「集中查看 + 跳转」，安排已有预览确认路径。

### D2 搜索关键字是否也匹配项目名（P4-06 §9.2）

**现状**：关键字只匹配**标题**。搜「Rust」不会带出该项目下名为「起步」的任务。

**要定什么**：命中项目名时，是否把该项目的任务也列为结果。

**怎么测**：一条纯函数用例即可判定，不需要跑浏览器。构造：项目 `{id:"p1", title:"Rust 入门"}` + 任务 `{title:"起步", projectId:"p1"}`，然后

```ts
buildDeadlineItemsFromIndex(index, today, { ...DEFAULT_DEADLINE_FILTER, query: "Rust" })
```

现在返回 `[]`；改成匹配项目名后会返回该任务。**这条用例本身就是判据**，改与不改都建议留下它，把口径钉死。

**代价**：会让「搜任务」变成「搜项目」，用户可能不理解为什么出现标题里没有该词的任务 —— 需要文案说明（例如结果行显示「所属项目命中」）。

**建议：先不加**，保持可预测；确有需要时改 `deadlines.ts` 里的一处谓词即可。

### D3 项目项在同日期内的排序（P4-06 §9.3）

**现状**：规格的排序链是「日期 → 类型 → `sortOrder` → 稳定 ID」，但 `Project` **没有** `sortOrder` 字段。P4-06 的做法是：项目在同日期同类型内按**标题**升序，最后用源 ID 收尾。

**要定什么**：项目这一级用「标题升序」还是「纯稳定 ID」。

**怎么测**：两条断言，成本极低：

1. 同日期同类型的两个项目 `"B"`、`"A"` → 断言顺序为 `["A","B"]`（现有用例覆盖了这个方向）。
2. **把 `workspace.projects` 数组顺序颠倒 → 断言输出完全不变**。这条现在**没有**，而它才是「确定性全序」的真正判据 —— 防止未来有人把比较器写成依赖输入顺序。

**建议**：保持标题升序（可预测、人类可读），**补上第 2 条断言**。

### D4 `calendarSummary.deadlineUrgency` 是否改用日历运算（P4-06 §9.4）

**现状**：`src/lib/calendarSummary.ts:119-120` 用固定 24 小时推算：

```ts
const milliseconds = new Date(`${deadline}T12:00:00`).getTime() - new Date(`${today}T12:00:00`).getTime();
return milliseconds <= 7 * 86_400_000 ? "soon" : "later";
```

**这是真 bug，不只是口径不统一**：两个本地正午之间的毫秒差在夏令时切换周**不等于** `N × 24h`。秋季回拨（多出 1 小时）时，「正好 7 个日历日之后」的截止日会算成 `608,400,000 > 604,800,000` → 被判成 `later`（「未来截止」），而它应该是 `soon`（「7 天内截止」）。只影响日历标记的文案与样式，不影响任何事实。

**怎么测 —— 先纠正一个我一开始弄错的结论**：**DST 在本机是可以运行时复现的**。`TZ=America/New_York node ...` 这种**环境变量前缀无效**（沙箱把 TZ 剥掉，`process.env.TZ` 仍是 `undefined`、时区恒为 `Asia/Shanghai`），但在 **Node 进程内部**赋值立刻生效：`node -e "process.env.TZ='America/New_York'; ..."` → `getTimezoneOffset()` 从 240 变 300。

实测证据：`2026-10-25` 到 `2026-11-01`（北美夏令时结束那天，本地日 25 小时）正好 7 个日历日，却算得 `608,400,000 > 604,800,000` → 判成 `later`（应为 `soon`）。

测法两步（照 `src/lib/review.timezone.test.ts` 的既有做法）：

1. **一条 Vitest 用例**：`beforeAll` 里 `process.env.TZ = "America/New_York"`、`afterAll` 还原（Vitest 默认按文件隔离进程，不外溢），断言边界日判成 `soon`；并先断言目标日确实是 25 小时，防止时区没生效时空跑。
2. **把日差抽成纯日历函数**（`localDaysBetween`），`deadlineUrgency` 改用它；再加一条**结构性护栏**读源文本，断言不再出现 `86_400_000` 这类固定毫秒日长（照 `nativeBuildConfig.test.ts` 的先例）。

**建议：改。** 成本极低，消除一处与截止页新口径的分叉；同时把「本机无 DST、无法运行时证伪」写进报告，与 P4-06 报告 §7 的既有已知局限保持一致。

### D5 「回到现在／目标时段显露」是否写浏览偏好（P4-05 §9.1）

**现状**：P4-05 的「程序性滚动不写偏好」闸门放行了**优先级 2**（用户点「回到现在」、或跨页把目标时段带到眼前）。也就是说：被带到某处后，下次打开会回到**该处**。

**要定什么**：这是「用户明确请求的落点」，还是应该像恢复记忆／三日缓冲平移一样不写偏好。

**怎么测**：扩展现有 E2E「restores each timeline view's browsing position after a restart」，加两条对照：

1. 进入日历 → 手动滚到某处 → 重载 → 断言恢复到该处。
2. 进入日历 → 点「回到现在」→ 重载 → 断言落在「现在」（保持写偏好）**或**回到第 1 步的手动位置（改为不写）。

两条一起跑，口径就被钉死了；只跑一条会留下歧义。

**建议：保持写偏好。** 它是用户主动发起的定位，符合「我把它带到哪就记住哪」。

## 4. 附：两条与「怎么测」直接相关的本机实测事实

1. **`TZ` 只在「进程内部赋值」时生效**：`TZ=... node` 这种 shell 前缀会被沙箱剥掉（`process.env.TZ` 为 `undefined`、时区恒为 `Asia/Shanghai`），但在 Node/Vitest 里 `process.env.TZ = "..."` 立刻生效。所以 **DST 相关行为在本机是可以运行时证伪的** —— 用 `beforeAll` 切时区即可，`src/lib/review.timezone.test.ts` 已经是这个做法。对 D4 这类缺陷，运行时用例 + 结构性护栏两者都建议有。
2. **Playwright 默认不录 trace**（`PW_TRACE=1` 才录），`run-e2e.mjs` 启动前会把 `test-results/` 残留用 rename 挪进 `_quarantine/`。原因是沙箱 safe-delete 有「单轮 50 条」上限，trace 的 screencast 逐帧 jpeg 会让一次运行产出约 2,000 个文件、把下一次启动堵死。改测试基础设施时别把这两道去掉。

## 5. P4-07 引擎留下的五个待定项：评估与建议

来自 `phase-4-p4-07-implementation.md` §9。逐条给出「现状 / 选项 / 建议 / 原因」。**前四条建议「保持现状」，只有一条附带小改动** —— 因为引擎刚被 36 条用例钉死，没有具体反例之前不该动它。

### 5.1 待续是否包含「只有待回顾、没有任何进度事件」的任务（P4-07 §9.1）

- **现状**：**包含**。引擎按规格字面实现 —— 周期内有「未完成推进」**或**「待回顾／未推进／跳过事实」的 active 任务都算待续。
- **选项**：A 保持包含；B 只保留「真的推进过但没完成」。
- **建议：A，保持包含。**
- **原因**：
  1. 规格 §7.2 的待续定义**明确把「待回顾」列为合格事实**，改成 B 就是偏离规格；
  2. 产品目标是**降低"重新安排"的阻力**。计划了却没做的任务，恰恰是最需要被重新安排的那一批 —— 把它藏起来，用户得自己去日历里翻；
  3. 排除它会让「待续」退化成「半途而废清单」，与「不靠羞耻感施压」的产品原则相冲。
- **可补的小改动**：如果页面想说明**为什么**它在待续（是"没推进"还是"推进了没完成"），`ReviewTaskDetail.carryover` 现在只是个布尔。建议 P4-08 顺手加 `carryoverReasons`（引擎小改），让页面能分类呈现；不加也能用，只是文案笼统。

### 5.2 已产生执行记录的 `missed` 时段不计入「未推进」（P4-07 §9.2）

- **现状**：**记录优先** —— 该时段一旦有执行记录，就不计入「未推进」。
- **选项**：A 保持（记录优先）；B 显式状态优先（用户标了"未推进"就永远算未推进）。
- **建议：A，保持记录优先。**
- **原因**：
  1. 执行记录是**更硬的事实**。那一格真的投入了时间，再把它算成「未推进」，汇总会自相矛盾 —— 「未推进 3 项」里有一项明明记着 40 分钟投入；
  2. 规格 §7.2 要求「关联发生项与 session **去重**」，A 正是去重的体现；
  3. B 会产出「你未推进」而用户其实做了的反馈，这是本产品最忌讳的惩罚性提示。
- **可补的小改动**：担心用户「我明明标了未推进」的话，页面可以在该时段显示「**已补录执行记录**」而不是静默吞掉（需要引擎给出这个标记）。

### 5.3 `notes` 的中文措辞（P4-07 §9.3）

- **现状**：引擎直接给出中文口径说明（设备时区名、项目过滤、并行记录、同一时刻事件、有计划但未记录），页面原样展示。
- **选项**：A 页面原样展示；B 页面自己写一套短文案。
- **建议：A，但允许在引擎里改短。**
- **原因**：
  1. 口径说明必须**只有一份** —— 规格 §7.4 反对「维护三份不一致算法」，措辞同理；组件里另写一套，将来改口径必然漏掉一边；
  2. 规格 §7.2 明确要求页面**显示当前时区说明**，所以这段文字是必须出现的，不是可选项；
  3. 只要求保留「**执行记录累计**」与「**未记录**」两个关键说法，其余可以缩短。
- **落地**：要改就改 `review.ts` 里的字符串（一处），**不要在组件里覆盖**。

### 5.4 `ReviewResult.milestones` 是否够用（P4-07 §9.4）

- **现状**：只给冻结结果／当前达成 + `resultText`。
- **建议：先按现状实现，不够再加。**

## 6. P4-08 报告 §9 的五个待定项：评估与建议

来自 `phase-4-p4-08-implementation.md` §9。**五条全部「保持现状」→ 本批零代码改动**（2026-10-16 用户确认）。

判断的出发点与 §5 一致：这些都不是缺陷，而是"还可以怎样"的偏好题；**没有具体不适之前不动已经跑通的代码**。

### 6.1 周期标题文案 → 保持

- **现状**：当前周「本周回顾」、非当前周「8月3日 — 8月9日回顾」、日「8月5日回顾」、月「2026年8月回顾」。
- **原因**：这不是随意混用，而是同一套规则 —— **当前周期用相对说法，其它周期用绝对日期**。统一成日期范围会让当前周变啰嗦（「8月10日 — 8月16日回顾」不如「本周回顾」好读）；反过来全用相对说法又说不清"哪一周"。

### 6.2 明细区焦点落点 → 保持（聚焦容器）

- **现状**：打开明细后聚焦明细区容器（`tabIndex=-1`），Tab 从容器进入第一个控件。
- **原因**：这是 WAI-ARIA 的标准「区域聚焦」模式 —— 屏幕阅读器先朗读"这是什么区域"（容器有可访问名称），再让 Tab 进入第一个控件。直接聚焦「关闭」按钮会让键盘用户先听到"关闭"而不是内容。

### 6.3 项目筛选是否跨重启 → 保持不跨重启

- **现状**：项目筛选（引擎 `projectId`）只放 App 层内存，重启回到「全部项目」。
- **原因**：
  1. 与截止页筛选**同规则**（P4-06 已定：同会话跨页有效、重启不恢复）。两处行为一致比各自"更优"更重要 —— 用户不会记得"这个页面的筛选会记住、那个不会"；
  2. 筛选是「我此刻在看什么」的**临时视角**，不是偏好。周期与锚点是"我想固定看哪一段"，筛选不是；
  3. 代价不对称：加一个 `AppSettings` 字段要牵动设置持久化、备份偏好快照与 AC16 的慢写／错误回归，为一个临时视角付这些不值。
- **这是五条里唯一会影响 P4-09 验收范围的一条，保持即无影响。**

### 6.4 `notes` 是否缩短 → 保持原样

- **现状**：页面原样展示引擎 `notes`。
- **原因**：实际文案里**常驻的只有一句**（`进度事件按当前设备本地时区分桶…`，规格 §7.2 明确要求页面显示当前时区说明），另外四句**全部带条件**（项目过滤／并行记录／同一时刻事件／有计划但无记录），只在对应情况出现时才提示。不啰嗦，无需缩短。
- **若日后要改**：改 `review.ts` 的那几处字符串（口径只有一份），**不要在组件里另写一套**。

### 6.5 回顾页是否只读 → 保持提供动作

- **现状**：明细区提供「编辑」「安排」「定位项目」，与截止页一致。
- **原因**：
  1. 与截止页一致；
  2. 回顾的价值正是「看到没推进的 → **当场重新安排**」。拿掉动作就只剩"看"，正好回到产品要解决的痛点（**知道但做不了**）；
  3. 这三个动作作用于**任务**，不是改写回顾数据本身，因此不违反「回顾是只读投影」。

### 6.6 结论

五条全部保持，**零代码改动**。P4-09 可以直接开跑，验收范围不受影响。

## 7. P4-09 报告 §9 的三条待定项：评估与建议

来自 `phase-4-p4-09-implementation.md` §9。**三条已于 2026-10-16 拍板**。

### 7.1 sequential（最坏情况）口径不算进预算 → 保持 isolated 稳态判据

- **现状**：预算判据用「每项独立起页」的 isolated 口径（月回顾 max 47–78ms）。同一页面上连着测三项的 sequential 口径下，月回顾 P95 117.4ms、max 142.8ms，超 100ms。
- **建议：不算进预算，保持 isolated 判据。**
- **原因**：
  1. 规格 §8 的措辞是「月回顾计算 ≤100ms（**预热后** 20 次）」—— 稳态口径；规格**没有定义页面复用**。按最坏情况判，等于引入一个规格里不存在的判据。
  2. **证据指向别处**：月回顾**纯计算**只要 6.6–8.4ms，页面上却要 25–142ms —— 差额全在渲染与堆压力，**不是回顾页的统计公式**。按 sequential 判会把「浏览器堆里堆着前序 DOM 残骸时的 GC 变慢」误记成「回顾页算得慢」，**修也会修错地方**。
  3. **而且它并不更"真实"**：独立复核测到 isolated 口径在**机器带负载**时也会到 93.7ms（余量 6%）。真正敏感的是**整体负载**，不是是否复用页面 —— 换成 sequential 判据只会让读数更抖，不会更接近用户感受。
  4. 规格 §12 对 S2 的处理本就是「记录影响、替代路径和后续任务」→ **不阻塞发布**。
- **落地**：保留为已知边界；P4-10 真机复测时确认「用户是否可感」（**至少跑两次**：一次空闲、一次带负载）。若真机确认可感，再谈分帧渲染 —— 那是**修性能**，不是改验收标准。

### 7.2 日历网格 ARIA 缺陷 → 单开一个小工作包（P4-11），不并入 P4-10

- **现状**：`role="gridcell"` 缺 `role="row"` 祖先（周视图的 `.day-track` 挂在 `role="region"` 下；月视图 42 个格子直接挂在 `role="grid"` 下），axe 报 `aria-required-parent`（critical）与 `aria-required-children`。
- **建议：单开 P4-11**（提示词：`phase-4-p4-11-kickoff-prompt.md`）。
- **原因**：
  1. 规格 §12 明确 **S2 不阻塞发布**。
  2. **P4-10 的性质是验收与发布。** 在里面改产品代码，会让「已验证安装包」对应的代码在发布前又变一次 —— 隔离验收、视觉证据、真机性能复测都要重跑。**验收包里改代码是最贵的做法。**
  3. **它不是一行改动**：要把周／月网格重排成 `grid → row → rowheader／gridcell`，并决定时间轴、全天区、拖拽预览这些非单元格子节点怎么标注 —— 会牵动 P4-03 的月历与 P4-04 的周网格，需要自己的回归与 axe 证据。
  4. 影响面已如实记录：**不影响视觉与键盘用户**（方向键、`PageUp`／`PageDown`、`Enter` 语义照常），单元格 `aria-label` 已含完整日期时间；受影响的是屏幕阅读器读不出「第几行第几列」。
- **落地**：P4-10 把 S2 写进已知边界，**并在发布说明里写明这条已知无障碍缺陷**（规格 §13 有先例）。顺序上**建议 P4-11 在 P4-10 之前完成** —— 发布包包含修复、AC14 的 axe 证据干净。
- **已落地（2026-10-16）**：P4-11 已完成，且**在 P4-10 之前**。月视图改成标准 `grid → row → columnheader／gridcell`；周视图选**方案 B（不声称网格）** —— 日列与时间光标用 `role="group"` + 可访问名，选中态走 `aria-current`。`e2e/phase1.spec.ts` 的两个「已记录缺陷」常量已删除，日／周／月三条视图在 960×200% 下浅／深两色 axe 全部零违规；改前／改后 4 张日历截图**逐字节相同**（零像素变化）。**因此 P4-10 的发布说明不再需要写这条已知缺陷。** 探针另外发现一条**未修**的对比度缺陷（`.calendar-actual-record` 白字 2.82，修它要改配色），见 [`phase-4-p4-11-implementation.md`](phase-4-p4-11-implementation.md) §7.1。

### 7.3 `output/` 过程文件 → 关键证据入库，过程文件不入库

- **现状**：报告引用了 `output/` 下的截图与性能 JSON，而 **`output/` 是 gitignored 的** —— 别人 clone 下来，报告里所有引用都是**死链**。
- **建议：关键证据入库，过程文件留在 `output/`。**
- **原因**：

## 8. P4-11 报告 §10 的两条待定项：评估与建议

来自 `phase-4-p4-11-implementation.md` §10。**两条已于 2026-10-16 拍板**。

### 8.1 对比度缺陷（`.calendar-actual-record` 白字 2.82）→ 单开 P4-12，在 P4-10 之前完成

- **现状**：浅色主题 + 开启「显示实际记录」时，实际记录叠加层是**白字配 `#da845e` 底**，对比度 **2.82**（< 4.5:1），axe `color-contrast`（serious，WCAG 1.4.3 AA）。深色主题不违规。
- **成因**：该叠加层把 `color: var(--action-text)`（为**实色** `--action` 按钮配的白色）用在一个**被稀释过的**背景上 —— `background: color-mix(in srgb, var(--accent) 82%, var(--panel))`。混色之后底色变浅，白字压不住。
- **建议：单开 P4-12**（提示词：`phase-4-p4-12-kickoff-prompt.md`），**在 P4-10 之前完成**。
- **原因**：
  1. 它是**真实的 WCAG AA 违规**，用户只要打开「显示实际记录」就会遇到 —— 不是理论问题。
  2. **修法不止一种，而且每一种都会改变视觉**（A 文字改深／B 底色换成实色／C 提高混色比例），需要一次专门的前后对照与两主题实测 —— 不是顺手改一行，因此不该塞进验收包。
  3. 与 P4-11 同理：**验收包里不改产品代码**（P4-10 的性质是验收与发布，改代码会让「已验证安装包」对应的代码在发布前又变一次）。
  4. **性价比**：带着它发布，发布说明要多写一条已知无障碍缺陷，P4-10 的真机浅／深色验收也要把它算进去；花一个小包修掉更干净。
- **必须带上的验收口径**：P4-09 的教训正是**验收夹具没开「显示实际记录」，所以这条缺陷从 AC14 眼里溜过去了**。P4-12 的 axe 用例必须**显式开启这一项、先断言 `.calendar-actual-record` 真的渲染出来，再断言零违规**，并覆盖浅／深 × 960×200%。

### 8.2 周视图方向键语义是否写进 UI-SPEC → 不需要

- **现状**：P4-11 判定「不需要」，理由是 UI-SPEC 的既有文本已经覆盖。
- **建议：同意，不改。**
- **已独立核对**：`docs/design/UI-SPEC.md` 写明「周视图键盘焦点在日期头之间用左右方向键移动，**在时间网格中用方向键移动到相邻日期或吸附时间**；`Page Up`／`Page Down` 切换前后周，`Enter` 对焦点所在标记打开详情、对空白时间执行既有创建小气泡，焦点移动不等同于创建或选择数据」—— 与实现一致，**没有缺口**。
