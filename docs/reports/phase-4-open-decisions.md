## 1. 需要拍板的

### D1 截止页是否常驻任务池（P4-06 §9.1）

**现状**：`App.tsx:348` 的 `hasTaskPool = page === "today" || page === "calendar" || page === "projects"` —— 截止页**不在**其中。截止页只提供行级「安排」动作（复用预选任务的排程入口，走预览确认），**不能拖拽**。

**要定什么**：截止页要不要像今日页一样常驻右侧任务池。

**怎么测**：把 `hasTaskPool` 加上 `page === "deadlines"`，然后：

```powershell
npm test
npm run test:e2e
```

重点看三处：(a) AC10 用例「跨页返回保留筛选／焦点／滚动」是否仍成立（滚动容器与焦点恢复会被新栏位影响）；(b) 960×640 与 200% 缩放下截止页的筛选是否仍可用（AC14）；(c) 新栏位会不会像今天修的那个问题一样遮挡头部 —— 检查 `#task-pool` 的 `position` 与 `getBoundingClientRect()`。

**真正的难点不在测试**：截止页没有时间轴，「拖到哪」没有语义。要么任务池只是摆设（不能拖，那它的价值基本为零），要么需要重新设计三栏布局与拖拽落点 —— 规格 §6.2 没有定义这件事。

**建议：不加。** 截止页的定位是「集中查看 + 跳转」，安排已有预览确认路径。

### D2 搜索关键字是否也匹配项目名（P4-06 §9.2）

**现状**：关键字只匹配**标题**。搜「Rust」不会带出该项目下名为「起步」的任务。

**要定什么**：命中项目名时，是否把该项目的任务也列为结果。

**怎么测**：一条纯函数用例即可判定，不需要跑浏览器。构造：项目 `{id:"p1", title:"Rust 入门"}` + 任务 `{title:"起步", projectId:"p1"}`，然后

```ts
buildDeadlineItemsFromIndex(index, today, { ...DEFAULT_DEADLINE_FILTER, query: "Rust" })
```

现在返回 `[]`；改成匹配项目名后会返回该任务。**这条用例本身就是判据**，改与不改都建议留下它，把口径钉死。

**代价**：会让「搜任务」变成「搜项目」，用户可能不理解为什么出现标题里没有该词的任务 —— 需要文案说明（例如结果行显示「所属项目命中」）。

**建议：先不加**，保持可预测；确有需要时改 `deadlines.ts` 里的一处谓词即可。

---

### D3 项目项在同日期内的排序（P4-06 §9.3）

**现状**：规格的排序链是「日期 → 类型 → `sortOrder` → 稳定 ID」，但 `Project` **没有** `sortOrder` 字段。P4-06 的做法是：项目在同日期同类型内按**标题**升序，最后用源 ID 收尾。

**要定什么**：项目这一级用「标题升序」还是「纯稳定 ID」。

**怎么测**：两条断言，成本极低：

1. 同日期同类型的两个项目 `"B"`、`"A"` → 断言顺序为 `["A","B"]`（现有用例覆盖了这个方向）。
2. **把 `workspace.projects` 数组顺序颠倒 → 断言输出完全不变**。这条现在**没有**，而它才是「确定性全序」的真正判据 —— 防止未来有人把比较器写成依赖输入顺序。

**建议**：保持标题升序（可预测、人类可读），**补上第 2 条断言**。

### D4 `calendarSummary.deadlineUrgency` 是否改用日历运算（P4-06 §9.4）

**现状**：`src/lib/calendarSummary.ts:119-120` 用固定 24 小时推算：

```ts
const milliseconds = new Date(`${deadline}T12:00:00`).getTime() - new Date(`${today}T12:00:00`).getTime();
return milliseconds <= 7 * 86_400_000 ? "soon" : "later";
```

**这是真 bug，不只是口径不统一**：两个本地正午之间的毫秒差在夏令时切换周**不等于** `N × 24h`。秋季回拨（多出 1 小时）时，「正好 7 个日历日之后」的截止日会算成 `608,400,000 > 604,800,000` → 被判成 `later`（「未来截止」），而它应该是 `soon`（「7 天内截止」）。只影响日历标记的文案与样式，不影响任何事实。

**怎么测 —— 先说一个本机实测结论**：**DST 在这台机器上无法用运行时复现**。实测 `TZ=America/New_York`（含 `env` 与 `export` 两种写法）后，Node 里 `process.env.TZ` 仍是 `undefined`、`Intl.DateTimeFormat().resolvedOptions().timeZone` 仍是 `Asia/Shanghai`、`getTimezoneOffset()` 恒为 `-480` —— 环境变量被沙箱剥掉了。所以「写一条跨 DST 的 Vitest 用例」在这里**做不到**。

可行的测法两步：

1. **把日差抽成纯日历函数**（例如 `localDaysBetween(from, to)`，用日历字段／`Date.UTC` 整数运算），单测它；`deadlineUrgency` 改用它。DST 正确性由此**由构造保证**，不依赖运行环境。
2. **加一条结构性护栏**：读 `src/lib/calendarSummary.ts` 源文本，断言不再出现 `86_400_000`／`* 24 * 60 * 60 * 1000` 这类固定毫秒日长。仓库已有先例 —— `src/lib/nativeBuildConfig.test.ts` 就是读 `Cargo.toml` 守一个「看起来没用其实必需」的配置。

**建议：改。** 成本极低，消除一处与截止页新口径的分叉；同时把「本机无 DST、无法运行时证伪」写进报告，与 P4-06 报告 §7 的既有已知局限保持一致。

### D5 「回到现在／目标时段显露」是否写浏览偏好（P4-05 §9.1）

**现状**：P4-05 的「程序性滚动不写偏好」闸门放行了**优先级 2**（用户点「回到现在」、或跨页把目标时段带到眼前）。也就是说：被带到某处后，下次打开会回到**该处**。

**要定什么**：这是「用户明确请求的落点」，还是应该像恢复记忆／三日缓冲平移一样不写偏好。

**怎么测**：扩展现有 E2E「restores each timeline view's browsing position after a restart」，加两条对照：

1. 进入日历 → 手动滚到某处 → 重载 → 断言恢复到该处。
2. 进入日历 → 点「回到现在」→ 重载 → 断言落在「现在」（保持写偏好）**或**回到第 1 步的手动位置（改为不写）。

两条一起跑，口径就被钉死了；只跑一条会留下歧义。

**建议：保持写偏好。** 它是用户主动发起的定位，符合「我把它带到哪就记住哪」。

### D6 导航入口位置（P4-06 §9.5）

**现状**：「截止事项」放在「日历」与「项目」之间，当前顺序为 今日 → 日历 → 截止事项 → 项目 → 7 天回顾 → 数据 → 设置。

**要定什么**：位置本身没有对错，属产品偏好。

**怎么测**：两条约束可测，且都已有覆盖：(a) `PAGE_IDS` 与导航表逐项一致（`settings.test.ts` + `App.test.tsx` 的「导航入口逐项可达并可跨重启恢复」）；(b) 960×640 与 200% 缩放下 7 个入口全部可达（`.sidebar nav` 自身可滚动）。换位置只需改 `App.tsx` 导航表一处，然后跑 `npm test` + `npm run test:e2e`。

**建议**：保持现状（动线是「从今天 → 到全局」，截止事项紧跟日历之后）。

## 4. 附：两条与「怎么测」直接相关的本机实测事实

1. **`TZ` 在本沙箱被剥掉**，Node 恒为 `Asia/Shanghai` → **DST 相关行为无法在本机运行时复现**。凡是「只在夏令时切换周才错」的逻辑，本机只能靠**构造性保证 + 结构性护栏**守住，不能靠跑用例证伪。D4 即属此类。
2. **Playwright 默认不录 trace**（`PW_TRACE=1` 才录），`run-e2e.mjs` 启动前会把 `test-results/` 残留用 rename 挪进 `_quarantine/`。原因是沙箱 safe-delete 有「单轮 50 条」上限，trace 的 screencast 逐帧 jpeg 会让一次运行产出约 2,000 个文件、把下一次启动堵死。改测试基础设施时别把这两道去掉。
