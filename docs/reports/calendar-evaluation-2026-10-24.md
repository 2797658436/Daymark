# 日历页面评估与整改方案

评估日期：2026-10-24。文档状态：**整改方案已定稿，实施未开始**。轮次划分（A/B 两轮）与四项设计决策（D1–D4）已于 2026-10-24 按推荐值定案，见 §5.1 与 §6；本轮只产出评估、量测证据与本文档，未修改产品代码、未提交 Git，用户工作区中 `src/App.tsx`／`src/styles.css` 等未提交修改原样保留。

评估对象：`src/App.tsx` 的 `CalendarPage`／`ContinuousDayView`／`DayCalendarGrid`／`CalendarDay`／`CalendarSession`／`CalendarTimeBlock`／`MonthCalendar`（约 1075–1830 行）、`src/styles.css` 日历段（约 538–697 行）、`src/hooks/useCalendarViewport.ts`、`src/lib/calendarTimeline.ts`／`calendarPlacement.ts`／`calendarDrag.ts`／`timelineDrag.ts`／`pendingPlacement.ts`。

对照基准：`docs/design/UI-SPEC.md` 的「日历视图」「拖拽排程」两段，以及 2026-10 以来「设置／数据／回顾／项目／任务池」五轮优化沉淀出的设计语言（见 §3）。

## 1. 结论摘要

用户的三个体感——**拥挤、日视图不好用、拖拽有大问题**——全部被量测证实，且各有明确的结构性根因，不是观感偏差：

1. **拥挤是真的，而且集中在「网格之前的 chrome」和「周视图列宽」两处。** 1200×800@100% 下，页头 + 工具栏 + 网格内吸顶头合计吃掉 276px（窗口高的 34.5%），真正画时间的只有 458–488px；200% 缩放下 chrome 吃到 453–657px（56%–82%），周视图还被迫横向滚动。周视图在 1200 宽、任务池停靠时列宽只有 **94px**，比 960 宽（111px）还窄——任务池停靠反而让主工作区更挤，与 UI-SPEC「中央区域不足时优先收起右侧面板」相反。
2. **日视图的第一体感坏在「进入即午夜」。** 打开日视图，滚动位置落在当天面板的 00:00（实测 `scrollTop` 恰好等于三日缓冲中间面板起点 1822 / 总高 5466），12 条安排全在屏幕外，右下角「回到现在」常亮。首次定位请求被三日缓冲的初始写入吞掉了。叠加 92px 的双层吸顶日期头（同一天写了三遍日期）与一屏只有 6.8 小时，日视图变成「先滚半分钟才能干活」。
3. **拖拽是两套输入通道、五处状态、三遍互不一致的计算。** 换位置走 HTML5 DnD、改时长走 pointer events；预览与提交各算一遍且用的时段集合口径不同；UI-SPEC「拖拽排程」段约 30 条目标里有 9 条未实现（让位动画、拖拽中时间读数、跨时段确认、拖入时间块确认、拖回池落区、多选整组等），还有一处**静默丢弃 drop** 的分支（在卡片中央松手但未触发半秒 latch 时，什么都不发生）。

整改分**两轮**（§5）：**A 轮「改呈现」**＝页头与工具栏合并、日视图进入即现在 + 单屏 8 小时、周视图列宽与截断治理（F01–F03、F05–F08、F11、F12，约 2.5–3 天含验证）；**B 轮「改输入通道」**＝拖拽统一为 pointer 自绘并补齐规格缺口（F04、F09、F10、F14，约 4–6 天含测试重写）。分轮的理由不是工作量而是**回归归因与回滚边界**：B 轮要重写约 5 个组件拖拽用例 + 两个 E2E 文件的拖拽段，与 A 轮的布局改动同轮落地时红了无法归因，且拖拽是产品核心回路、出问题时只想回滚拖拽那一半。月视图密度（F13）与多选整组拖拽留到后续包。

## 3. 设计基准：已优化页面给出的语言

从 `review-page.tsx`／`project-rail.tsx`／`deadlines-page.tsx`／`settings-ui.tsx`／任务池与 `styles.css` 对应段提炼，作为日历整改的对齐目标（括号为出处）：

1. **页头去 eyebrow，标题即事实**：回顾页标题就是周期本身、项目页标题下挂「N 个项目 · M 个临期」副标题；日期／计数只写一遍（`review-page.tsx:474-477`、`App.tsx:2251-2255`；用户 2026-10-22 反馈「左上角头重」）。
2. **一行筛选条，不造第二行 chrome**：截止页／项目页共用 `.deadline-filters`（搜索 + 排序 chips + 筛选 chips 一行），页面不额外加工具栏卡（`styles.css:1589-1605`）。
3. **同一句话不写两遍；没话说整节不渲染**（`review-detail.tsx:175-176`、`review-page.tsx:396-398`）。
4. **行内不放写入口，只读投影 + 下钻气泡**（`review-page.tsx:402-406`）。
5. **宁可隐藏标题也不裁按钮**；命中区四档：44 常驻 → 40 气泡 → **2.125rem(34px) 紧凑** → 28 图表（`styles.css:376-386`、`:709`）。
6. **首屏高度只由「有没有」决定，不由「有几条」决定**；不可控条数降级为一行提示 + 浮层（`review-page.tsx:230-239,595-596`）。
7. **放得下就别折叠**（`review-page.tsx:44-49`）。
8. **container query 挂外层包裹查后代**；界面缩放走 rem、图表几何走 px（`styles.css:1049-1054`、`:1174`）。
9. **字号下限 12px**：UI-SPEC「任何密度都不把可读文字缩到 12px 以下」；已优化页面最小档是 `.72rem`（11.5px 仅用于刻度与角标），正文与卡片文字 ≥ `.75rem`。
10. **卡片语言**：14px 圆角 + `--line-soft` 描边 + `--shadow-low` 静止卡；卡头 = 色点 + 名称 + 右侧「N 项 · 合计」；强调色只给选中／今天／链接，主体文字不用强调色（`styles.css:1402-1417`、`:1425-1426`）。

日历页当前与这套语言的差距见 F02、F05、F11。

## 4. 问题清单

### F01 · P0 · 进入日视图落在 00:00，首次定位被三日缓冲吞掉

**现象**：打开日视图（无论全天还是默认时段模式），视口顶部是当天 00:00；12 条安排、当前时间线全在屏幕外；`cal-day-full-1200.png`／`cal-day-full-960.png` 里右下角「回到现在」常亮。实测 `scrollTop=1822` 恰等于 `scrollHeight 5466 / 3`（三日缓冲中间面板起点），`firstVisibleMinute=0`。

**根因**：两条写入互相竞争且没有仲裁。`ContinuousDayView` 的 layout effect 在 `[anchor]` 变化时**直接写** `axis.scrollTop = middleStart`（`App.tsx:1245-1256`），并调用 `onProgrammaticPosition()` 声明「这是程序性滚动」；而 `useCalendarViewport` 的首次定位（优先级 6）在 `useLayoutEffect([view])` 里 `queue("initial", …)`（`useCalendarViewport.ts:447-457`），落地要靠下一帧 rAF。`applyPosition` 在 `pickTrack` 取不到轨道时 `return true`（`useCalendarViewport.ts:407-408`）——**把「还没量到」当成「已成功」**，意图被丢弃；即便量到了，三日缓冲那次直接写也会在同一帧序列里把结果顶回 `middleStart`。周视图没有三日缓冲，所以周视图进入落点正常（`firstVisibleMinute=478`），问题只在日视图。

**冲突**：UI-SPEC「今日页进入时让当前时间位于视野中央附近」的同等预期适用于日视图；产品原则「降低开始的操作阻力」。2026-09-06 的 GUI 评估已记录过周视图「初始落在午夜」，日视图这条同源且更严重。

**整改**：① `applyPosition` 的 `!track` 分支改为 `return false`（保持待处理、交给 ResizeObserver），不得返回 true；② 三日缓冲的初始写入不再直接写 `scrollTop`，改为向仲裁入口提交一个优先级 4 的请求，让「进入恢复（5）／首次定位（6）」能排在它之后；③ 补一条 E2E：进入日视图后断言视口中心分钟 ∈ 现在 ±90 分钟（锚点=今天）或首个安排 ±60 分钟（锚点≠今天）。

### F02 · P0 · 页头 + 工具栏 14 个控件两行，chrome 占窗口 23%–57%

**现象**：页头一行 6 控件（日/周/月、上一段、回到今天、下一段）+ eyebrow「手动排程」；工具栏一行 8 控件（默认时段/全天、紧凑/标准/详细、显示实际记录、时间块、吸附）。100% 下两行共 126px；960×640 工具栏折成 115px；**200% 下工具栏 285px、页头 110px，网格前 chrome 453px = 窗口高的 56.6%**（`cal-day-full-200.png`：工具栏里「默认时段／全天」「紧凑／标准／详细」每个分段都竖排成两行）。网格内还有第三层吸顶（F05），三层 chrome 叠完，200% 日视图只剩 214px 画时间。

**根因**：`.calendar-toolbar` 是一个独立的 `flex-wrap` 圆角卡（`styles.css:564`），8 个控件平铺无收敛策略；分段控件按钮 `min-height:36px` + `padding:.35rem .8rem`（`:569`）在 200% 下宽度翻倍即折行。页头与工具栏职责重叠：日期范围在工具栏左、视图切换在页头右，用户要两行之间来回看。

**冲突**：基准 1、2（一行筛选条、标题即事实）；基准 5（紧凑档命中区）；UI-SPEC「日历与拖拽操作应获得最大的可用空间」。

**整改**：合并为**一行**：页头标题直接写当前范围（日：`8月5日 周三`；周：`8月3日 — 8月9日`；月：`2026年8月`，学回顾页），右侧 `日/周/月` 分段 + `‹ 今天 ›` 一组；删 eyebrow。工具栏降级为视图内状态条：左=该视图特有的显示模式（仅日视图有「默认时段/全天」）+ 密度三档（用 2.125rem 紧凑档）；右=「显示实际记录」开关保留可见，**时间块与吸附收进一个「显示 ⋯」气泡**（低频，基准 5/21）。目标：100% 下网格前 chrome ≤ 120px，960×640 与 200% 均单行不折。

### F03 · P0 · 周视图 1200 宽列宽 94px，比 960 还窄；三并行卡片 23px

**现象**：`cal-week-1200.png` 七列各 94px（卡片 86px），触发 `.calendar-session` 的全部四档容器查询（124/112/100/88px，`styles.css:662-665`）→ 卡片只剩标题，时间、进度、状态文字全被藏掉；18:00 的三项并行每张只有 **23px** 宽（`sessions.widths=[86,23]`），完全不可点读。960×640 下任务池转覆盖面板，列宽反而 111px。

### F09 · P1 · 拖拽两套通道、五处状态、预览与提交各算一遍 —— **已收口（B1／B2）**

**现象**（代码调研）：换位置 = HTML5 DnD（任务池→日历 `copy`／日历内 `move`／拖回池取消，`App.tsx:1033`、`1799`、`930-932`）；改时长与时间块整块 = pointer events（`App.tsx:1613-1672`、`1776-1796`、空白框选 `1505-1508`）。状态散在五处：`CalendarDay.dragPreview/dragSourceId`（列级）、`weekGhost/dayGhost`（网格级 `1092/1240`）、`calendarDrag.active`（模块级影子副本）、`pendingPlacement`（模块级 external store）、`CalendarTimeBlock.resize/landed`（组件级）；清理靠 5 个 `useEffect` 各自监听 window `dragend/drop` 兜底。`previewFromDrag` 在 dragover 与 drop 各跑一遍（`1455-1492`、`1511`），`placeCalendarItem` 用 `insertionChanges` 第三遍重算（`App.tsx:448-465`），且**预览用全部 sessions、提交只取 `scheduled|missed`**（`1420` vs `456`），两套集合不一致时预览与落库不同。

### F19 · P1 · 日历卡片正文是全站最小字号（A5 验收后登记，用户裁决）

**现象**：卡片正文 `.75rem`（12px），而 body 基准 14px、任务池标题 13.1px；standard 84px/小时下 60 分钟卡 84px 高塞 3 行 18px 行预算。用户验收 A5 时的原话：「目前标准的话太挤了，标准应该为紧凑，然后标准至少还要再放大 2 倍」。

**整改**（A6，定案 D9/D10）：日视图 presets 改 84/168/216（区间上限 240），周视图 presets 不动；卡片字号随档——日 12/14/16px、周 12/13/14px，行高 rem 表达，A5 的高度容器查询断点按档重写。

### F20 · P2 · 视觉细账四项（A5 验收后登记）

**现象**：① 折叠条高度 `COLLAPSED_GAP_HEIGHT = 44` 是 px 常量而日期带是 2.75rem，200% 下 44 vs 88 不等高；② 日视图连续轴同一条 2px 横溢来自 `.time-block-delete`（`scrollWidth 32 / clientWidth 20`）撑宽卡片逐层上传（A2 §2.1 遗留）；③ 状态条右组复选框标签顶对齐、「显示 ⋯」按钮满高，垂直不齐；④ 详细档高卡内容顶对齐、进度条 `absolute` 钉底，中间一大片空。

**整改**（A6）：① 折叠条高度改由 `preferences.scale` 推单一来源并内联下发；② 删除按钮改绝对定位不贡献 `scrollWidth`；③ 右组 `align-items: center`；④ 进度条进文档流紧跟内容，卡底留白 ≤1 行高。周 200% 的 74px 列与日期头折行、任务池 200% 裁切、F13 月视图**裁决为接受/留后续**，不进 A6。

### F21 · P2 · 改时长不走让位与确认（B2 验收后登记） —— **已收口（B3）**

**收口记录（2026-10-26）**：已收口（B3）。让位走 `resizeChanges`（与插入同一份级联），确认走 `buildDecision` 的 resize 分支，提交由 App 的 `resizeCalendarSession` 写成一次事务 + 一个撤销项。契约、gate 与反向验证见 [`calendar-b3-implementation.md`](calendar-b3-implementation.md)。

### F22 · P2 · 折叠悬停展开与边缘滚动互相拉扯（B2 验收后登记） —— **已收口（B3）**

## 5. 整改轮次与实施顺序

### 5.1 为什么是两轮，而不是一轮或四轮

- **一轮装不下的不是工作量，是回归归因。** B 轮要重写 `App.test.tsx` 的 5 个拖拽用例、`e2e/phase1.spec.ts` 的拖拽段（42/462/538 行等）与 `e2e/gui-optimization.spec.ts` 的 296/365 行护栏；与 A 轮的布局改动同轮落地时，任何一条红都无法判断是 chrome 改动还是拖拽通道改动。拖拽是产品核心回路，出问题时只想回滚拖拽那一半——只有分轮才回滚得干净。
- **拆成四轮又浪费。** W1/W2/W3 共享的风险面只有 `styles.css`，彼此不叠加；但每轮都要付一次固定验证成本（headless 截图逐张看 + 960×200% 浅深 axe + 探针复测，约半天）。拆三轮等于把这份成本付三遍。
- **仓库自己的先例就是这个粒度**：P4-11/12/13 明确拆成「收口的三小包」各自带报告；项目页（`0200029`）、回顾页（`2e8e857`）、任务池（`3573bf4`/`b49242b`）各是一轮一带提交。A/B 两轮与这个节奏同构。
- **A 轮内部再分 4 步**，每步独立绿 + 独立截图，任何一步打架都可以单独后移而不削弱其余（尤其第 1 步 F01 若与 P4-04/P4-05 仲裁不变量打架，可整体挪去 B 轮）。

| 轮次 | 范围 | 工期（含验证） | 回滚边界 | 完成的判定 |
