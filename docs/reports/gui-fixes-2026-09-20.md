# GUI 缺陷修复记录（2026-09-20）

用户报告的缺陷，都在此前已落地的工作里。分两轮：第一轮修月视图、时间块回弹与桌面拖拽配置；
第二轮（实机反馈后）找到「已排卡片拖不动」的真正根因，并修掉跨列落点闪烁与待回顾气泡。

版本：2.0；状态：**已修复并通过工程验证**；实机验收项见第 4 节。

## 1. 自动排程后月视图看不到排程结果（P1）

**现象**：自动排程写入执行时段后，月视图里既看不到周六／周日两列，点开有内容的那天格子里也是空的。

**根因有两个，互相独立：**

### 1.1 详情面板盖住了月历最右几列

`styles.css` 的 `@container (max-width: 1040px)` 分支把「已选日期」详情面板改为**绝对定位覆盖层**
（`position: absolute; inset: 0 0 0 auto`）。覆盖层压在月历上，把它右边几列挡住 —— 既看不到也滚不到。

复现测得（1200×760）：详情面板左缘 **x = 501**，而月历列一直排到 **~820**，
于是 **周四、周五、周六**三列的右边缘（512 / 615 / 718）都落在面板下面。

**修复**：在覆盖层那一支里给日历**让出**面板所占宽度 —— 靠 `padding-right` 留白，覆盖层正好落在留白里
（绝对定位的包含块是 padding box，`right: 0` 即留白右缘）。同时放开会被顶回覆盖层下面的
`min-width`（`.month-calendar` / `.week-calendar-main` / `.week-sticky-header`），并让月历与周视图的列
可以收缩（`minmax(0, 1fr)`）。≥1040px 时走原来的并排布局，行为不变。

### 1.2 月历格子根本不体现「当天安排」

`calendarDaySummary()` 只汇总截止、项目截止、里程碑、完成、推进、未推进 —— **完全没有「当天安排」**。
所以排程结果只出现在右侧详情面板里，格子必然是空的。这是设计覆盖面上的缺口，不是渲染故障。

**修复**：`calendarDaySummary` 新增 `scheduled` 摘要项，排在最前（月历首先回答「这天要做什么」），
标签形如 `安排 4 项 · 19:00 起`（按当天最早开始时间提示）。

计数只取 `status === "scheduled"`：`missed`（未执行）与 `cancelled` 各自已有条目，不能重复算成「安排」。

**证据**：新增 E2E 用例先复现（三列被盖，报出 `周四(512 > 501)` 等）后转通过；新增单测锁定
`安排 2 项 · 14:00 起`、排序取最早、以及 missed／cancelled 不计入。

## 2. 时间块移动松手后有动画错误（P2）

**现象**：拖动时间块、松开鼠标的瞬间，卡片会回弹一下再跳到新位置。

**根因**：松手时 `resize` 归 `null`，`displayStyle` 立刻回落到 `baseStyle` —— 而 `baseStyle` 取的是
**尚未更新的旧时间**（父级 workspace 要等写入返回才变）。与此同时 `.is-resizing[data-resize-edge="move"]`
提供的「跟手不缓动」过渡覆盖被解除，`.calendar-time-block` 的 `top .2s` 过渡恢复生效，
于是卡片带着过渡**平滑地弹回旧位置**，等数据回来再跳一次。

**修复**：把落点记进 `landed` 状态，松手后**渲染落点**（而不是旧位置），直到 `block` 真的变成它。
这样既没有回弹，又保留了「吸附到落点」那段应有的平滑动画。新一次拖动开始时会清掉 `landed`，
避免写入失败时卡在陈旧位置。

**证据**：新增单测把 `updateTimeBlock` 挂成永不返回的 Promise —— 正是「松手到数据回来之间」那段窗口 ——
断言卡片停在落点 `13:15`。补渲染修复前，该用例失败在旧位置（`expected 41.67 to be close to 55.21`）。

## 3. 桌面版拖不动已排好的卡片（P1，阻断）

**现象**：release 桌面版里，日历上已排好的任务卡完全拖不动；同一份代码在浏览器里正常。

**根因**：`src-tauri/src/lib.rs` 的 `disable_webview_external_drop()` 显式调用了
`ICoreWebView2Controller4::SetAllowExternalDrop(false)`。当初的理由是「关掉原生外部拖放，
页面内的 HTML5 拖拽才会工作」。

**这个方向是反的。** `AllowExternalDrop = false` 禁止的是该 webview 的**一切**拖拽，
页面内部的 HTML5 拖拽一并被禁掉：

- [MicrosoftEdge/WebView2Feedback#4830](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4830)：
  *"Setting AllowExternalDrop = false ... will block any drag"* —— 包括 WebView2 内托管的页面内容。
- [tauri#9445](https://github.com/tauri-apps/tauri/issues/9445)、
  [tauri#15138](https://github.com/tauri-apps/tauri/issues/15138)：
  `dragDropEnabled: true` 才会劫持拖放；要用 HTML5 拖拽就得设 `false`。
- 源码事实：wry 0.55.1 全仓**只有一处** `SetAllowExternalDrop`，且只在拖放处理器存在（即
  `dragDropEnabled: true`）时才调用 —— 我们的显式调用是唯一一次、且方向错误的干预。

也就是说，`tauri.conf.json` 里的 `dragDropEnabled: false`（`492c6c9` 设置）**本来就是对的**。

**修复**：

- 删除 `disable_webview_external_drop()` 整个函数与 `.setup()` 里的调用；
- 移除因此引入的仅 Windows 直接依赖 `webview2-com`、`windows-core`；
- 在原调用点留下说明，写明「不要碰 AllowExternalDrop」及其原因，避免再被「修」回去。

**证据**：外部权威证据（上述三条）＋源码事实。**注意：我无法在本环境验证桌面拖拽手感**
（需要真实 WebView2 与鼠标操作），这一项必须由你在 release 实机上确认。

> **第二轮更正（同日，实机反馈后）**：这一节的结论**仍然是错的**，但错在另一层。
> `dragDropEnabled: false` 本身是对的（保留），移除 `SetAllowExternalDrop` 也保留 ——
> 但它们都**不是**这次「卡片拖不动」的原因。真正的根因在应用自己，见 §3b。

## 3b. 第二轮：已排卡片拖不动的真正根因（P0）

**现象**（第二次反馈）：时间块上下拖动可以，**已排卡片完全拖不动**；跨列拖动时动画会闪。

**定位过程**：写真实鼠标拖拽探针（`locator.dragTo` ＋ 手动 `mouse.move`），在 Chromium 里录
`dragstart` / `dragenter` / `dragover` / `dragend`，再逐项隔离变量：

| 变体 | 观察到的序列 | 结论 |
| --- | --- | --- |
| 原样 | `dragstart` → **`dragend`**（同一轮里立刻取消），没有任何 `dragenter` | 拖拽被取消 |
| 把 `.calendar-session` 克隆到 `body` 再拖 | `dragstart` → `dragenter` → `drop` | 元素与 CSS 本身没问题 |
| 只覆盖 `pointer-events: auto` | `dragstart` → `dragenter@另一个 day-track` | **就是它** |
| 只覆盖 `transform` / `opacity` / `filter` | 仍然立刻 `dragend` | 这三个无关 |
| 在卡片上截断 pointerdown／mousedown 传播 | 仍然立刻 `dragend` | 不是祖先事件处理器 |
| 位移很小（指针仍停在卡片上） | 能出现 `dragstart`；位移一大连 `dragstart` 都没有 | 解释了大跳位移造成的假象 |

**根因**：`.calendar-session.is-dragging-source { pointer-events: none }`。
这条类由 `onDragStart` 里的 React 状态（`setDragSourceId`）加上，而浏览器在**整个拖拽期间**
都会用指针位置去命中拖拽源：源一旦不可命中，Chromium 在 `dragstart` 之后立刻取消这次拖拽。
时间块用的是 pointer 事件（自己监听 `pointermove`），完全不受影响 —— 这就是
「上下可以、卡片不行」的全部原因。任务池卡片的 `onDragStart` 不触发任何状态更新，
不会给自己加上这条类，所以它的真实拖拽一直是好的（E2E 的 `dragTo` 用例覆盖）。

**修复**：去掉 `pointer-events: none`，只保留变淡（`opacity` / `filter` / `transform` 都不触发取消），
并在 CSS 里写明这条约束，避免以后再被当成「拖动时别挡住落点」的优化加回来。

**护栏**：`e2e/gui-optimization.spec.ts` 新增真实指针拖拽用例，断言 `dragstart` 之后**没有**紧跟着
`dragend`（拖拽还活着），且源卡片在拖动期间仍然可命中。反向验证：把 `pointer-events: none` 加回去，
用例报 `dragstart 之后拖拽立刻被取消：["dragstart@calendar-session…","dragend@… is-dragging-source"]`。

### 3b.1 顺带修掉：真实浏览器里拖拽没有任何反馈

`previewFromDrag` 在 `dragover` 里用 `dataTransfer.getData(...)` 判断「正在拖什么」。而 HTML 规范规定
`dragenter` / `dragover` 期间 dataTransfer 处于**保护模式**：`types` 可读，`getData()` 一律返回空串
（只有 `dragstart` 与 `drop` 能读到）。所以真实浏览器里跟着鼠标的落点卡、插入线、
「悬停 0.5 秒以同时安排」提示**从来不会出现** —— 现有 E2E 用手搓 `DataTransfer` 的合成事件，
恰好绕开了这条规范。

**修复**：新增 [`src/lib/calendarDrag.ts`](../../src/lib/calendarDrag.ts)：`dragstart` 时把负载
（kind／id／抓取偏移）记一份影子副本，`dragover` 回落到它，`drop` 阶段仍优先用 `dataTransfer` 真值。
影子副本只在 `types` 里确实带着日历自己的类型时生效，从窗口外拖文件进来不会凭空造出预览。

### 3b.2 跨列落点的「闪」

时间块跨列松手时，源列那一份仍按旧时间渲染（落点覆盖只处理同一天），于是卡片带着刚恢复的过渡
**弹回源列**，等写入回来再跳到目标列。

**修复**：落点跨天时把这一份原地隐藏，用 portal 把落点卡片画进**目标列的 `.day-track`**
（坐标直接复用 `position()`）；数据追上后本实例连同 portal 一起卸载、目标列渲染真身，
在同一次提交内完成。拖动中卡片改为**横向按整列吸附**（纵向仍自由跟手），松手不会再横向跳一下；
写入失败时撤掉落点覆盖，回到事实位置。

**护栏**：`App.test.tsx` 用「永不返回的写入」把整段窗口摊开，断言源列那份 `display: none`、
目标列的 `.is-landed` 有正确 top／height、拖动中 `left` 吸附到目标列。反向验证：去掉隐藏那一步即失败。

## 3c. 待回顾动作气泡（按反馈理顺）

**原来的逻辑**：`onPointerEnter` / `onFocus` 直接打开，`onPointerLeave` / `onBlur` 延迟 200ms 关闭；
气泡是 `position: fixed` 的独立 portal，位置靠 scroll／resize 监听重算。四个问题：

1. 鼠标扫过日历就会冒出一串气泡，盖住下面的卡片；
2. 指针从卡片移到「更新进度」的滑块上就可能触发关闭，用到一半气泡消失；
3. 键盘 Tab 进气泡会让卡片失焦 → 200ms 后气泡关闭 → 焦点掉到 body，键盘用户根本走不通；
4. 位置靠估算（`rect.left - 2`），和卡片边缘对不齐。

**现在**：气泡改用 `FloatingPanel`（`kind="action"`）—— 锚定卡片、随滚动实时跟随，
Esc／点外部／动作完成统一交给浮层宿主关闭。**打开只在明确手势**：点卡片本体，
或聚焦卡片上的「待回顾」入口按钮后回车（该按钮的 `aria-label` 仍是「待回顾」，与状态文字同名）。
键盘契约不变：卡片上的 `Enter` 仍是「编辑时间」（阶段 4 AC02）。
