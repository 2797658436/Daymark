## 2. 版本号：为什么调成 0.1.1

规格 §12 允许「若调整则同步」，也允许「保持不动但写明理由」。这里**选择调整**，理由是可核对的，不是偏好：

1. **回退目标与候选版必须能区分。** 两者都叫 0.1.0 时，`artifacts/` 里会出现两个同名不同内容的 exe，只能靠改文件名区分，而「应用和功能」里两个版本号完全一样 —— 覆盖升级／回退的实测结果就无法用版本号自证。
2. **AC18 要求「覆盖升级」可复现。** 0.1.0 → 0.1.1 是一次真实的版本变更：注册表 `DisplayVersion`、`Daymark.exe` 的 `FileVersion`、安装包文件名三处同时变化，升级前后一眼可验（见 §5）。
3. 规格 §12 的措辞本身就是「版本号若调整，同步 package.json、Cargo.toml、Tauri 配置及锁文件相关版本」——这四条同步已全部完成。

**没有顺手改的东西**：`src-tauri/Cargo.toml` 的 `indexmap = { version = "1.9", features = ["std"] }` 原样保留（删了原生层会以 E0107 编译失败，`nativeBuildConfig.test.ts` 盯着）；`Cargo.lock` 里只有 `daymark` 这一条版本行变化，其它依赖版本一个没动。

## 3. 打包：必须套 MSVC 环境

```bash
bash scripts/with-msvc-env.sh npm run tauri build
```

- **为什么必须套**：本机 PATH 上没有 MSVC 的 `link.exe`，只有 Git Bash 自带的 GNU coreutils `link.exe`；`rustc`（`x86_64-pc-windows-msvc`）按名字调用 `link.exe` 时会命中 GNU 那个，报 `link: missing operand` 之类与真实原因无关的错误。脚本把 MSVC + Windows SDK 排到 PATH 最前并补齐 `LIB`／`INCLUDE`，还额外校验 `command -v link.exe` 解析到的确实是 MSVC 那个。
- **实测耗时**：整条命令 **2m17s**（release 依赖已缓存；其中 `Compiling daymark` → `Finished` 1m46s，`makensis` 约 20s）。与规格／提示词里写的「约 2 分 20 秒」一致。
- **产物**：`Daymark_0.1.1_x64-setup.exe`（4,284,778 B）。裸可执行文件同批产出 `daymark.exe`。
- 旧包**没有被覆盖**：`artifacts/Daymark_0.1.0_x64-setup.exe` 的 SHA256 与开工前逐字节一致（§1.3）。
- 打包过程日志：`docs/reports/phase-4-p4-10-implementation/tauri-build.log`（`EXIT=0`）。

## 4. 隔离方式：旁置个人数据 + 全新数据目录

### 4.1 先确认能不能用「独立 Windows 账户」

- 本机是 Windows 11 专业版，当前进程**是管理员**，理论上可以 `net user` 建账户；但「建账户 → 首次登录生成 profile → 以另一用户令牌启动 GUI 程序 → 再删账户」这套动作对用户机器的改动，远大于本包需要验证的东西，而且 `Start-Process -Credential` 启动的进程默认不在当前交互桌面，截屏与托盘都取证不了。
- Windows Sandbox 未安装（`WindowsSystem32\WindowsSandbox.exe` 不存在）。
- **结论：采用规格明确允许的另一条 ——「明确隔离的数据环境」。** 具体做法见 4.2，并且用 SHA256 证明个人数据**自始至终没有被打开过**。

### 4.2 具体做法（四步，全部可复核）

1. **记录指纹**：`%APPDATA%\com.daymark.desktop\daymark.db` = `6a54156b…ca74`（180,224 B）、`settings.json` = `f6e3021c…5daa5`（1,536 B），备份目录 7 份。见 `isolation-before.txt`。
2. **整体旁置**（同卷 rename，不删除、不复制）：
   - `%APPDATA%\com.daymark.desktop` → `…\com.daymark.desktop.hold-p4-10-20261017`
   - `%LOCALAPPDATA%\com.daymark.desktop`（WebView2 缓存）→ 同样加 `.hold-p4-10-20261017`
   - 旁置后立刻重算指纹，**与第 1 步逐字节相同**（rename 不碰内容）。
3. **全新数据目录**：应用启动时 `app.path().app_data_dir()` 发现目录不存在，`fs::create_dir_all` 新建，`Database::open` 建库并迁移到 v7。之后所有验收都发生在这个**新建**目录里，从没写过个人库。
4. **收尾还原**：验收结束 → 停进程 → 把验收期间的数据目录整体挪到 `…p4-10-acceptance-20261017`（保留证据）→ 把 `…hold-p4-10-20261017` 改回原名 → 重算指纹：`6a54156b…ca74` / `f6e3021c…5daa5`，**与旁置前逐字节一致**。

> **一处需要如实说明的副作用**：开工时用 Python 以 `mode=ro` 读过个人库，SQLite 因此在个人数据目录里留下了 `daymark.db-shm`（32,768 B）与 `daymark.db-wal`（**0 B**）两个瞬时文件。主库与设置文件的 SHA256 未变，两个瞬时文件不承载任何数据（WAL 长度为 0），应用下次打开会自行清理。

### 4.3 为什么这算「隔离」，而不是「跑了一遍没事」

- 个人库**从未被本轮的任何一个二进制打开**：数据目录在第一次启动前就被改名移走，验收期间应用看到的目录是新建的。
- 每一个状态都有**可核对的数字**（表计数、`db_sha256`、`settings` 键集合），不是「看起来正常」。见 §5、§6。
- 恢复类验收**没有一次是覆盖个人库**：所有 restore 的目标都是新建目录里的库。

| 项 | 做法 | 实际结果 |
| --- | --- | --- |
| **关闭驻留托盘** | 向主窗口发 `WM_CLOSE` | 窗口隐藏、**进程仍存活**（`daymark.exe` 在，WebView2 子进程在），托盘图标仍在通知区域 |

| **提醒后恢复** | 开启「执行提醒」（提前 10 分钟），造一条今天 23:11–23:41 的时段；启动后前端 30 秒轮询立刻命中 | 右下角出现系统通知「**即将开始：四级词汇导学 / 23:11–23:41，点击托盘图标回到 Daymark。**」（`ac17-02-reminder-toast.png`）；随后点托盘图标 → 应用**直接进入日历日视图并停在 23:08 那一格**，目标时段高亮（`ac17-03-reminder-restored.png`） |
| **目标不存在时回退** | 提醒已发出（原生已暂存目标）→ 把该时段从库里删掉 → 用一次真实写入（「安排今天」）刷新工作区快照，确认内存里已无该时段 → 隐藏窗口 → 点托盘图标 | 应用显示并落在**今日页**（不是隐藏前的「数据与安全」页），说明 `daymark-open-session` 找不到目标时确实回退到今日（`ac17-04-fallback-today.png`） |

### 7.1 取证方式的坦白说明

- 本机**没有**可用的 CDP：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=…` 被 wry 自己的 `additionalBrowserArgs` 覆盖，9222 端口从未监听（`Get-NetTCPConnection -LocalPort 9222` 无记录、WebView2 命令行里也没有该参数）。**没有**为了取证去改 `tauri.conf.json` 加调试端口 —— 那会把调试端口带进发布包。
- 本机沙箱**禁用 `Add-Type`**（运行时编译 .NET 代码）与 `Assembly.Load*`，所以 UIAutomation 的 PowerShell 路线也不通。最终用的是一个**只做四件事**的 ctypes 小工具（截屏／点击／按键／关窗口，`.workbuddy-ai/tmp/p410-win.py`，不入库），也就是「像人一样看屏幕、点鼠标」。
- 因此 §7 的每一项都是**真实点击、真实系统通知、真实进程状态**，不是脚本桩。代价是：**取证期间这台机器必须没人抢窗口**（本轮确实出现过用户切窗口导致点击落到别处的情况，重做后才有上面的证据）。

## 10. 已知边界（发布说明必须带上的）

### 10.1 P4-09 留下的两条（S2／S3，未修）

1. **sequential（最坏情况）口径下月回顾超预算**：同一页面上先做大量重活、再立刻打开月回顾时，P95 117.4 ms / max 142.8 ms（预算 100 ms）。**判据仍用 isolated 稳态**（每项预算独立起页、预热后取样），本轮两次复测均达标。影响：只有那一条路径的首绘可能超过 100 ms；引擎纯计算只有 10.9–13.0 ms，说明差额在渲染与堆压力。替代路径：正常使用是「先打开回顾页、再切周期」，即 isolated 口径。后续任务：若要收口，方向是回顾页数值表分帧渲染或复用已挂载的行，**不改统计口径**。
2. **1200 宽 × 200% 应用内缩放下，截止页筛选复选框的第一次鼠标点击会落空**（S3）：焦点态改变盒子尺寸（`getBoundingClientRect().y` 269.2 → 301.7），`mouseup`／`click` 落到祖先容器上。**只在 1200×200% 这一格复现**；再点一次即生效，键盘路径（Tab + 空格）一直正常。后续任务：单独查焦点态布局位移，**不要**为它改缩放范围或预设。

### 10.2 P4-13 留下的三条（S2／S3，未修）

1. **200% 下短于约 35 分钟的时间块，标题仍是被裁的 12px**。`.calendar-time-block` 的 `min-height: 28px` 与 `@container (max-height: 26px)` 阈值是一对耦合常量：抬高 `min-height` 会让 `time` 越过 26px 阈值显形、把标题从 12px 挤成 0px（两次「只换单位」都被实测否定，已回退）。彻底修需要把阈值也换成 `rem`，代价是 100% 下某段时长的隐藏行为变化，属设计决策。详见 `phase-4-p4-13-implementation.md` §12.1。
2. **`.calendar-time-block` 的 `@container (max-height: 26px)` 阈值仍是 px**（与上一条同一根因）。
3. **`App.tsx` 的 `height: max(duration/1440*100, 1.25%)` 下限折算恒为 0.3 × hourHeight（21.6px）**，不随界面缩放走。它目前**低于** CSS 下限，不是约束方；一旦 CSS 下限降到 21.6px 以下，它会接管。

### 10.3 本轮新增的边界

1. **0.1.0 与 0.1.1 的可见差异**：0.1.0（2026-10-15 构建）早于 P4-08，导航标签是「7 天回顾」、没有回顾页的日／周／月；0.1.1 是「回顾」。回退到 0.1.0 后这些**界面能力**会消失，但**核心事实不受影响**（§5）。
2. **提醒的取证窗口很窄**：提醒只在「距开始 0–10 分钟」触发，且每次运行周期内同一时段只提醒一次。要在实机复现必须现造一条「马上开始」的时段；本轮用三条样本才走完「恢复」与「回退」两条路径。
3. **`artifacts/` 里的 0.1.0 在本轮开工前从未在这台机器上安装过**（注册表没有 Daymark 的卸载项，只有 `%APPDATA%` 里的数据目录与 `src-tauri/target/release/daymark.exe`）。也就是说「上一份已验证安装包」的**安装路径**是本轮第一次实测。
4. **真实使用（21 天验证方案）仍未验收**：本包只证明「工程通过 + 隔离桌面验收通过 + 可回退」，**不**等于「长期使用有效」。状态仍是「待真实使用验收」。
