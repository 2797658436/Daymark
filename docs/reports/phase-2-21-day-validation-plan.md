# Daymark 阶段 2 检测与 21 天验证方案

## 1. 目的

本方案用于判断 Daymark 阶段 2 是否同时满足以下两个条件：

1. **工程上可交付**：构建、自动化测试、安装、数据持久化、备份恢复和六个阶段 2 能力均可靠。
2. **产品上值得继续**：连续使用 21 天后，Daymark 确实降低了选择下一项、开始行动和错过后恢复的阻力，而没有变成需要频繁维护的额外负担。

工程验收通过不等于 21 天体验已经验证。本方案要求先通过技术门槛，再用固定版本进行连续真实使用，最后根据事实决定进入阶段 3、修复后复测或调整产品方向。

## 2. 检测范围

阶段 2 包含六个能力域，共 24 条编号验收标准：

| 能力域 | 验收标准数 | 主要验证问题 |
| --- | ---: | --- |
| 自动排程 Lite | 5 | 草案是否可靠、可理解、可撤销，能否减少寻找空档的负担 |
| 轻量时间块 | 3 | 是否如实占用容量，又不会被误当成任务或进度 |
| 基础重复习惯 | 5 | 发生项是否独立、不会累积欠账，能否进入既有执行闭环 |
| 错过后的挽救提示 | 3 | 是否只提示一次，四种动作是否安全，文案是否中性 |
| 简单最近 7 天回顾 | 3 | 是否如实呈现投入、推进、待续、未执行和跳过事实 |
| B 站链接导入 Beta | 5 | 公开分 P 是否可预览、编辑、选择并原子导入，失败后能否重试 |

同时检测阶段 2 依赖的基础能力：任务与项目、日历拖拽、执行记录、手动进度、设置持久化、托盘与提醒、SQLite 迁移、备份恢复、主题、缩放和基础无障碍。

不把阶段 3 的连续时间轴、月视图、默认时段折叠、时间轴缩放和完整拖拽体验列为阶段 2 缺陷。它们可以记录为体验需求，但不得导致阶段 2 验收误判。

## 3. 角色与环境

建议由同一名主测试者完成 21 天真实使用，以保证习惯和主观评分口径稳定；如有第二名测试者，可独立记录，不要把两人的天数或评分合并成一个样本。

准备以下环境：

- 一台日常使用的 Windows 设备，用于真实 21 天体验。
- 一个独立测试环境，用于恢复、损坏备份拒绝等可能替换数据的测试。可以使用独立 Windows 账户或明确隔离的数据副本，不在唯一的真实数据上做破坏性验证。
- 固定候选版本、提交哈希和安装包。21 天期间除阻断问题外不更换版本。
- 一份 Day 0 手动备份，并确认备份文件可以在独立环境中被识别和恢复。

## 4. 判定等级

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| S0 数据安全阻断 | 数据丢失、错误覆盖、恢复失败且无法回滚、应用声称保存但实际未保存 | 恢复后任务消失；进度被自动伪造 |
| S1 核心流程阻断 | 无法启动、持续崩溃，或六个阶段 2 能力中的核心路径无法完成 | 排程确认始终失败；无法结束执行 |
| S2 重要缺陷 | 有替代路径，但明显影响连续使用或使事实容易误解 | 习惯发生项重复；回顾统计明显错误 |
| S3 一般问题 | 不阻断任务完成的交互、文案或视觉问题 | 卡片拥挤；操作入口不易发现 |
| 建议 | 阶段 3 或后续优化，不属于阶段 2 缺陷 | 月视图、连续日期滚动 |

发现 S0 时立即停止在真实数据上继续操作，保留数据库、备份、截图和日志副本。发现 S1 时暂停 21 天计时；修复后从新候选版本的 Day 0 重新开始。S2/S3 可以继续记录，但不得在试用期间静默改变候选版本。

## 5. 第一关：候选版本技术门槛

### 5.1 固定候选版本

在仓库根目录记录：

```powershell
git status --short
git rev-parse HEAD
git log -1 --oneline
```

通过条件：

- 工作区干净；如必须携带未提交修改，应记录完整差异并把该状态视为新的候选版本。
- 提交哈希、测试日期、Windows 版本和候选安装包文件名已写入最终报告。

### 5.2 全套自动化与生产构建

运行：

```powershell
npm run check
npm run tauri build
```

通过条件：

- TypeScript 和 Vite 生产构建成功。
- Vitest、Playwright 和 Rust 测试全部通过。
- Tauri release 构建和 NSIS 安装包生成成功。
- 记录本次实际通过数量和耗时，不直接复制旧验收报告中的数字。
- 编译警告可以单独记录，但任何失败、跳过或不明原因退出都不算通过。

### 5.3 安装与启动冒烟

使用生成的 NSIS 安装包完成以下检查：

1. 全新安装并启动应用。
2. 创建一个仅含标题的任务，关闭窗口到托盘，再从托盘恢复。
3. 完全退出并重新启动，确认任务、设置和最后页面仍然存在。
4. 切换浅色、深色、200% 缩放和窄窗口，确认主要操作仍可见。
5. 创建手动备份，并在独立测试环境中完成预览和恢复。

通过条件：没有 S0/S1；重启后没有任务重复、丢失或进度变化；恢复后的核心数据和设置与备份预览一致。

## 6. 第二关：结构化功能检测

以下场景在 21 天试用前执行一次。每个场景记录“通过／失败／受阻／不适用”、证据和问题编号。

### T01 自动排程 Lite

准备三个任务：一个近期截止高优先级任务、一个无截止任务和一个单次投入时长大于现有空档的任务；再创建一个时间块和一个已有执行时段。

检查：

1. 打开自动排程，确认候选顺序符合截止日期、优先级和任务池顺序。
2. 草案只使用未来 7 天的适用默认时段空档。
3. 草案不覆盖时间块或既有执行时段。
4. 空档达到最低时长但短于目标时，只生成一个较短时段，不自动补排剩余时长。
5. 取消预览不写入数据；确认后整批出现；撤销后整批消失。

通过条件：草案与提交后的日历一致，取消和撤销不留下孤立时段，既有安排没有被移动。

### T02 轻量时间块

检查：

1. 创建和删除一个时间块。
2. 确认它与任务执行时段在视觉和操作上可区分。
3. 确认它不进入任务池、不具有完成度、不计入 7 天回顾的任务成果。
4. 再次自动排程，确认该时间块占用的容量不会生成重叠草案。

通过条件：时间块只表达“此处不可用”，不产生任务、进度或投入事实。

### T03 基础重复习惯

分别创建每天、工作日和每周选日的习惯，至少一个设置固定开始时间。

检查：

1. 每个日期拥有独立发生项，普通任务池中没有出现重复习惯任务副本。
2. 安排今天的发生项并走完开始、结束与进度闭环。
3. 跳过另一个发生项，确认没有完成或删除内部任务。
4. 重启应用，确认状态保留。
5. 再次自动排程，确认相同习惯日期不会产生重复时段。
6. 查看过去日期，确认错过的发生事实不会复制为多份今日欠账。

通过条件：每个发生日期只有一个明确状态，安排、完成和跳过互不混淆。

### T04 错过后的挽救提示

先确认“开始签到”和“挽救提示”均已开启，并设置一个便于测试的宽限期。对四个独立测试时段分别检查：

1. “现在开始”只创建真实的开始记录。
2. “延后 10 分钟”只调整该时段，不改变任务完成度。
3. “重新选择时间”允许用户确认新的安排。
4. “本次跳过”保留任务，不把任务标记为完成。
5. 关闭应用再打开，已经展示过的同一提示不会持续出现。
6. 关闭开始签到后，过期时段不会被系统擅自推断为未执行。

通过条件：四种动作都只改变其声明的事实；提示非模态、只出现一次且没有羞辱性表达。

### T05 最近 7 天回顾

准备至少一条实际执行、一条手动进度变化、一条未执行或跳过事实，以及一个仍需继续的任务。

检查：

1. 窗口恰好覆盖今天及之前六天。
2. 页面先显示完成／推进成果和待续，再显示每日事实。
3. 实际投入只来自执行记录，不从媒体时长或计划时长推算。
4. 没有签到的日期不会被换算成失败、零分或负面评价。
5. 在空数据环境中显示安静空状态。

通过条件：回顾内容可以逐项追溯到真实操作，没有自动评价或虚构数据。

### T06 B 站链接导入 Beta

使用一个包含多个分 P 的普通公开视频链接，以及一个无效或无法读取的链接。

检查：

1. 成功读取后先进入预览，不立即写数据库。
2. 修改一个标题、取消选择一个分 P，再确认导入。
3. 只创建一个普通项目和被选中的有序任务。
4. 每个任务保存对应分 P 链接和媒体时长；媒体时长不成为实际投入或完成度。
5. 失败后原链接仍保留并可重试，文本课程导入不受影响。

通过条件：预览前不写入、确认后一次写入；失败或取消不会留下半个项目。

### T07 长期数据与桌面行为

检查：

1. 对任务、项目、执行时段、习惯、设置分别做一次修改并重启应用。
2. 完成关闭到托盘、托盘恢复、显式退出和再次启动。
3. 触发一次执行提醒和一次启动摘要，确认它们不自动开始任务或改变进度。
4. 刷新每日备份，确认数据页没有遗留虚假成功或旧错误状态。
5. 在独立测试环境恢复备份，核对任务数、项目数、进度和关键设置。

通过条件：所有已确认操作均持久化，未确认操作不产生事实，恢复前后数据含义一致。

## 7. 第三关：21 天真实使用验证

### 7.1 Day 0：建立基线

开始前记录以下信息：

- 候选提交哈希、安装包和开始日期。
- 当前使用的替代方法，例如纸笔、系统日历或其他待办工具。
- 当前任务池中至少 8 个真实任务，覆盖有截止日期、无截止日期、不同优先级和不同预计耗时。
- 至少两个真实默认时段和一个真实时间块。
- 至少一个愿意连续使用的重复习惯。
- 开始前的三项困难评分，1 表示几乎没有困难，5 表示非常困难：
  - 决定下一步做什么。
  - 按计划真正开始。
  - 错过计划后重新进入行动。
- 创建 Day 0 手动备份。

### 7.2 日常使用规则

21 天内把候选版作为主要计划工具，不为凑数据虚构完成度或投入时间。

每天尽量完成：

1. 第一次打开时查看今日页和临近截止任务。
2. 有未安排任务时主动查看一次自动排程草案；不合适可以取消或撤销。
3. 按真实情况创建时间块、移动安排或跳过习惯。
4. 只在本人确认后开始、结束和调整完成度。
5. 当天结束时用两分钟填写每日记录。

允许中断使用，但必须如实记录原因。没有任务的一天不算失败；“活动日”定义为至少发生一次真实的创建、编辑、安排、执行、进度更新、习惯处理或回顾，而不是只启动应用。

### 7.3 21 天覆盖要求

这些要求用于保证能力被实际遇到，不作为用户表现评分：

| 能力 | 21 天内最低覆盖 |
| --- | --- |
| 自动排程 | 至少在 3 个不同日期查看草案；至少确认一次、取消一次、撤销一次 |
| 时间块 | 至少创建 3 个真实时间块，并让自动排程遇到其中一个 |
| 重复习惯 | 至少连续使用一个真实习惯 7 天；至少安排、完成或跳过各出现一次 |
| 挽救提示 | 至少在一个安全的真实或刻意延迟场景中出现；不要求为了测试伪造失败 |
| 7 天回顾 | Day 7、Day 14、Day 21 各查看一次并核对事实 |
| B 站导入 | 有真实课程需求时至少使用一次；没有需求时以 T06 结果作为功能结论，不影响整体产品验证 |
| 持久化 | 每周至少完整退出并重启一次，核对任务和设置 |
| 备份 | Day 0、Day 7、Day 14、Day 21 创建或刷新备份；恢复仅在独立环境验证 |

### 7.4 每日记录模板

每天复制一行：

| 日期 | 活动日 | 计划时段数 | 实际执行数 | 自动排程：查看/确认/撤销 | 挽救动作 | 手动重排次数 | 维护负担 1–5 | 下一步清晰度 1–5 | 主要事实或问题 |
| --- | --- | ---: | ---: | --- | --- | ---: | ---: | ---: | --- |
| YYYY-MM-DD | 是/否 | 0 | 0 | 0/0/0 | 无 | 0 | 1 | 1 |  |

评分口径：

- **维护负担**：1 表示几乎不用维护，5 表示为了维护计划而明显分心。
- **下一步清晰度**：1 表示仍不知道下一步做什么，5 表示下一步非常清楚。
- 只记录事实和体验，不使用“失败”“不自律”等评价性语言。

### 7.5 每周检查点

在 Day 7、Day 14 和 Day 21 回答：

1. 回顾页中的实际投入、进度、未执行和跳过是否与记忆及每日记录一致？
2. 哪一次自动排程建议最有帮助？哪一次最不合理？原因是什么？
3. 错过计划后，Daymark 是否帮助选择了下一步，还是增加了维护动作？
4. 有没有因为担心数据不可靠而回到其他工具？
5. 本周最想保留的一个能力和最想改变的一个摩擦点是什么？
6. 是否出现 S0、S1、S2 或重复三次以上的同类 S3？

Day 7 和 Day 14 只记录，不因普通体验问题修改候选版本。只有 S0/S1 修复才中止并重新开始验证。

## 8. 最终通过标准

### 8.1 工程通过

必须全部满足：

- `npm run check` 和 `npm run tauri build` 成功。
- T01–T07 全部通过，或仅存在已明确接受且不影响核心事实的 S3。
- 21 天内没有 S0/S1。
- 没有任务、执行记录、进度、习惯发生项或设置的无解释丢失、重复或自动伪造。
- Day 0 备份能够在独立环境中恢复，恢复后核心数据和设置核对一致。

### 8.2 产品验证通过

建议同时满足：

- 21 天中至少有 15 个活动日；中断原因不是应用可靠性或维护负担。
- Day 7、Day 14、Day 21 的回顾事实均能核对，没有系统性统计误导。
- 最后 7 天“维护负担”的中位数不高于 3。
- 相比 Day 0，三项困难评分中至少两项下降 1 分以上，且没有一项恶化 2 分以上。
- 测试者愿意在不被要求记录的情况下继续把 Daymark 作为主要计划工具。

这些阈值用于单人候选版决策，不代表统计学结论。增加测试者时应分别报告每个人的结果和共同出现的问题。

## 9. 决策规则

| 结果 | 决策 |
| --- | --- |
| 工程通过 + 产品验证通过 | 阶段 2 真实验证完成；可以根据 21 天摩擦记录排序阶段 3 里程碑 |
| 工程通过 + 产品验证部分通过 | 先修复最集中的 1–3 个摩擦点，进行 7 天定向复测，不直接扩展大范围功能 |
| 出现 S0/S1 | 阶段 2 不通过；修复、补自动化测试并从新候选版本重新开始 |
| 数据可靠但核心三目标没有改善 | 暂停阶段 3，重新检查产品假设，而不是仅用更多日历功能掩盖问题 |

阶段 3 的优先级应来自本次验证中的真实摩擦。例如，短时段不可读支持优先做卡片自适应；难以感知“现在”支持优先做状态感知；只有当拖拽本身成为主要阻力时，才优先投入完整拖拽排程。
