## 1. 结论摘要

一句话：**自动排程的算法是合格的，界面把它藏坏了。** 确定性排程引擎（`scheduling.ts`）按「截止 → 优先级 → 池序」贪心填空档、避开既有安排与时间块、支持部分安排，这些都与规格一致；但承载它的气泡把 66% 的高度花在候选清单之外、把 20 个候选压进一个 360px 的滚动窗、把「为什么排不上」全部吞成同一句「当前 7 天暂时放不下」，并且用**居中模态**把用户做决策最需要看的任务池和日历整个锁在背后。量测还挖出一条产品级缺陷：**截止日期已过的任务被自动排程永久排除**，而界面给的说法是「放不下」——恰好与 Daymark「降低重新安排的操作阻力」的核心原则相反。

用户的体感「这个气泡要重做」被量测证实为三类结构性问题：

1. **空间分配反了。** 1200×800@100% 下气泡 720×660：图标块＋标题＋说明＋容量条吃掉列表之前的 215px（33%），候选窗只有 360px（`max-height: 45vh`），而这 360px 里**还有 155px 是筛选行、搜索行、按钮行三个控件**（它们被放在滚动区内部，会跟着列表一起滚走），真正留给任务行的约 205px ≈ **3 行**；960×640 露 2 行；200% 缩放下列表前的 chrome 涨到 370px 而候选窗仍是 360px（`45vh` 不随根字号走），**只露 1 行**，且气泡自身开始滚动、主按钮落到首屏之外。
2. **选择语义与规格脱节。** UI-SPEC「自动排程交互」段 18 条里有 9 条未实现或只做了一半：没有「推荐本次安排／其他可安排」分组、没有「恢复推荐」、无法安排的项不折叠也不给原因、超选没有「超出 N 分钟」与名单、预览没有半透明建议卡／依据／移除／「仅应用已选」、没有「需要连续时段」。逐行的「可安排 N 分钟」读的甚至是**全量推荐计划**而不是用户当前的勾选。
3. **容器选错了。** 它是 `ConfirmDialog`（`kind="confirm"`，锁背景、`inert` 主界面），而自动排程在「应用」之前不写任何数据、应用后还能一次 `Ctrl+Z` 整体撤销——按本应用自己的分层（模态只留给恢复备份、结束本次这类不可逆动作），它应该是一个不锁背景的大气泡。

整改按五个工作包推进（§5）：**W1 容器与空间（把气泡还给候选）、W2 候选语义修正（含逾期任务这条产品缺陷）、W3 预览步重做、W4 视觉令牌与缩放、W5 入口与命名**。W1+W2 是止血包（约 2.5 天，不动 schema 与事务），W3+W4 约 1.5 天，W5 约 0.5 天。原文档列出的 5 个拍板点（§6）已于 2026-10-24 全部按推荐项定案：**D1=a**（逾期任务按窗口首日参与排档并标记）、**D2=a**（改非模态大气泡）、**D3=a**（预览拖动本轮不做）、**D4=a**（「需要连续时段」本轮不做并回写规格）、**D5=a**（习惯发生项收组）；定案后的实施顺序与验收口径见 §8。

## 3. 设计基准：已优化页面给出的语言

从 `review-page.tsx`／`review-detail.tsx`／`project-rail.tsx`／`deadlines-page.tsx`／`settings-ui.tsx`、任务池（`App.tsx:938–1010`）与 `styles.css` 对应段提炼，作为本次整改的对齐目标（括号为出处；与 [`calendar-evaluation-2026-10-24.md`](calendar-evaluation-2026-10-24.md) §3 同源）：

1. **标题即事实，不写解释段**：回顾页标题就是周期、项目页标题下挂「N 个项目 · M 个临期」；固定说明只出现在第一次需要的地方，之后收进 ⓘ 或副标题（用户 2026-10-22 反馈「左上角头重」）。自动排程现在用 44px 图标块 + 标题 + 一整行解释段 + 一整条容量横幅，四件事说了两遍（「不调整已有安排」在说明段与容量语义里各一次）。
2. **一行筛选条，不造第二行 chrome**：截止页／项目页共用一行「搜索 + 排序 chips + 筛选 chips」（`.deadline-filters`）；任务池把筛选做成三段 `.segmented compact`。自动排程用了「一个长得像任务行的下拉行 + 一个全宽搜索行 + 一行右对齐按钮」共 134px。
3. **同一句话不写两遍；没话说整节不渲染**（`review-detail.tsx`、`review-page.tsx`）。自动排程的容量条在零时段时写「使用 0 分钟 / 可用 0 分钟」，19 行各写一遍「当前 7 天暂时放不下」。
4. **不可控条数不占首屏**：待续名单、待回顾列表都降级为「一行提示 + 浮层」（`review-page.tsx` 的 `.review-pending-line`）。自动排程的 19 个候选与 7 天预览都是不可控条数，却直接平铺进一个 360px 窗。
5. **行内只读，写入口收进下钻**：回顾页行内不放写入口；任务池行的百分比是 44px 入口、点开锚定气泡。自动排程的候选行右半整片空白，既没有「已有 2 次未来安排」这类只读事实，也没有任何入口。
6. **命中区四档**：44 常驻（`.button { min-height: 2.75rem }`，`styles.css:376`）→ 40 气泡内（`.floating-panel .icon-action`，`styles.css:1582`）→ 2.125rem(34px) 紧凑分段（`styles.css:384`）→ 28 图表（`styles.css:709`）。自动排程的复选框是 16×16。
7. **卡片语言**：14px 圆角 + `--line-soft` 描边 + `--shadow-low` 静止卡（`.review-task-group`，`styles.css:1425`）；卡头 = 色点 + 名称 + 右侧「N 项 · 合计」（`.review-task-group-head`，`styles.css:1426`）；强调色只给选中／今天／链接。自动排程的行是 8px 圆角 + `--line` 实描边（`styles.css:1051`），筛选下拉也套了同一件「任务行」外衣。
8. **浮层分层**：`FloatingPanel` 的 `kind="editor"` 承载所有编辑器（任务／里程碑／习惯／时间块／默认时段，`floating-panel.tsx:7-12`），`kind="action"` 承载无草稿的动作与只读下钻（待回顾三操作 `App.tsx:1764`、回顾明细 `review-detail.tsx:380`、空白时段三入口 `App.tsx:1549`），危险确认是**锚定**的 `kind="confirm"` 小气泡（删里程碑 `App.tsx:2422`）；**居中模态 `ConfirmDialog` 只剩四个调用点**：继续安排、结束本次、恢复备份、自动排程（`App.tsx:1839/2754/2758/2542`）。自动排程在「应用」前零写入、应用后可整组撤销，却占了最重的一档。
9. **点空白即关，带草稿时再确认一次**：项目页浮层与完成记录气泡的既有约定（丢弃草稿前给一次锚定确认）。自动排程的勾选是纯临时状态，正好适用「点空白即关、关闭即丢弃勾选」。
10. **字号下限 12px；界面缩放走 rem、断宽度走 px**：已优化页面最小档 `.72rem` 只给刻度与角标（`styles.css:650,743` 一类）；断**宽度**用 px、断**行数／可用高度**用 rem（`UI-SPEC:144`、`styles.css:674-676`）；`@container` 挂外层包裹查后代（`styles.css:1049,1174,1303`）。自动排程的候选窗 `max-height: 45vh` 既不是 rem 也不是内容驱动，是 200% 下「只见 1 行」的直接原因。
11. **状态双编码、空状态分两种**：「无数据」给创建入口、「筛选无结果」给清除筛选（`.pool-empty` 的两支，`styles.css:523-527`、`App.tsx:993/996`）。自动排程只有一种空态文案，零时段与真无任务与筛选无结果共用一句「放不下」。
12. **高而不锁背景的panel已有现成先例**：回顾下钻气泡 `.review-detail-panel` 就是「flex 列 + 头/滚动体/底 + 底边淡出」的非模态大面板（`styles.css:1483-1496`：`padding:0`、`overflow:hidden`、`max-height:min(72vh,44rem)`、`.review-detail-body.is-scrollable` 的 mask 淡出）；`.floating-panel-wide` 已是 `min(44rem, 100vw - 24px)`（`styles.css:1571`），`.floating-panel .form-actions` 已是 sticky 底（`styles.css:1573`），`.floating-panel h2/header` 已是 sticky 头（`styles.css:1616`）。自动排程整改不需要新造容器语言，照这套拼即可。

自动排程当前与这套语言的差距见 F02、F05、F08、F09、F10。

## 4. 问题清单

### F01 · P0 · 逾期任务被永久排除出自动排程，界面只说「当前 7 天暂时放不下」

**现象**：夹具里「报销单据贴票」截止 2026-08-01（已逾期 4 天）、单次 20 分钟，未来 7 天有 27.5 小时空档，却在候选行里显示「当前 7 天暂时放不下」且永远无法被勾选生效；同窗口里 25 分钟的课程分 P 与 30 分钟的习惯发生项都拿到了时段（`candidates-1200.png`、`measurements.json` 的 `unschedulableRows: 1`）。

**根因**：`scheduling.ts:71` 的候选空档过滤 `(!item.deadlineLocal || gap.date <= item.deadlineLocal)`。窗口从「今天」起算，逾期任务的截止日期早于窗口首日，于是**没有任何空档满足条件**，`eligible` 恒为空 → 进 `unscheduledKeys`。这不是容量不足，是规则把「已逾期」等同于「不可安排」。

**冲突**：`CONTEXT.md` 产品原则「降低开始、重新安排和继续推进的操作阻力」与「今日界面优先呈现下一步可行动选择」；`UI-SPEC:208` 要求无法安排的项给出「缺少可用时长或约束冲突等确定性原因」——「截止日期已过」恰恰是最该说出口的原因，现在被吞成「放不下」。逾期任务正是防拖延工具最该接住的一批。

**整改（W2，D1 已定案 a）**：截止日期早于窗口首日的任务按「窗口首日」参与排档（`scheduling.ts:71` 的过滤改为先钳制 `deadline = max(deadlineLocal, startDate)`），候选行与预览卡打上「已逾期 N 天」标记（文字 + 图标双编码，复用 `deadlineLabel`，`App.tsx:2887`），容量摘要不计入惩罚措辞。同时把 `unscheduledKeys` 升级为**带原因的结构**：`scheduling.ts` 返回 `unscheduled: { key, reason, longestGapMinutes }[]`，`reason ∈ { below-minimum, no-slots, no-gap-that-day, fixed-start-busy, deadline-no-gap, gaps-too-short }`，供 F05 的折叠区逐条翻译成人话。补 Vitest：逾期任务能拿到时段且标记正确；六种原因各一条用例。

### F02 · P0 · 气泡 33% 高度是 chrome，候选窗只有 45vh
